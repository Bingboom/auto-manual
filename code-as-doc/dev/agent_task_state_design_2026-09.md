## 0. 结论摘要

- **Task Authority**：
  - 台账第 6 行自称“唯一执行状态入口”，来源登记的 `ledger` 域指向它，系统建设页也按它显示进度（已复核）。本稿建议确认台账为 REV 任务的状态权威，不另建。
  - 不在台账里的工作（大多数 fix/feat PR、Wukong 桥自己开的 PR）算不算 Task，现在是 UNCLEAR，列为开放问题。
- **十项能力的现状**（第 3 节）：
  - PARTIAL 七项：Task Authority、State Machine、Evidence、Resume、Acceptance、Audit Trail、Concurrency；
  - MISSING 三项：Claim、Checkpoint、Handoff。
  - 没有一项可以算 EXISTS。
- **SSOT 影响**（第 4 节）：
  - task_state 已经登记为 `ledger` 域，不新增域；
  - task_claim、checkpoint、handoff 作为 task_state 的子结构，记在方案二的任务记录里（第 16.1、16.3 节）；
  - acceptance 拆成两部分：验收策略是任务契约的字段，验收记录是证据；
  - human_decision 不在 REV-45 里建成独立域，按证据记录，并引用登记表、范围变更表等现有权威。
- **未来 V1 的候选做法（当前不实施）**：
  - 台账继续做唯一状态权威，所有状态变化只经一个受控入口；CI 对每个改台账的 PR 用同一套规则复查。
  - 认领、检查点、交接、证据和状态变化事件，写在每项任务一份只追加的记录里（第 5 节）。
- **历史试点候选**：REV-20（IDML 原生验收清单），理由和备选见第 15 节。REV-20 自身按原台账独立推进，不等待多 Agent。
- **历史选择**：第 16 节保留此前讨论及理由；重启时按届时实际系统重新确认，不把它当作当前待办。

## 4. SSOT Impact（需求第 30 节 C）

分类取值：(1) 独立事实域；(2) task_state 的子结构；(3) 只是证据；(4) 不属于 SSOT。

### 4.1 task_state

- **分类**：(1)，但已经登记为 `ledger` 域（执行进度），不新增域。
- **Fact**：每项任务的当前状态和状态词表。
- **Authority**：
  - REV 任务：台账状态列。依据是台账第 6 行“唯一执行状态入口”和来源登记的 `ledger` 域，都已复核。
  - 台账外的工作：不在 V1 范围（第 16.3 节决定），仍按 PR 规则和合并授权管理。
- **Writers**：今天是任何人经 PR。改为 agent 只经受控入口写；操作者可以手改，但 CI 用同一套规则复查。
- **Readers**：系统建设页、agent、操作者、以后的受控入口。
- **Derived Copies**：
  - 系统建设页的 `now_labels`、`rev:` 状态钉、note 和 summary 里的进度文字；
  - 台账第 4 节和文件头；
  - 设计文档的状态行；
  - 各 agent 的记忆。
- **Freshness**：RTD 构建时读 main；开着的 PR 看不到。
- **Conflict Rule**：以台账为准。页面副本与台账不一致时，今天只出“待复核”警告；建议以后在“当前在做”这类页面信息上改为由台账算出（第 17.4 节）。

### 4.2 task_claim

- **分类**：(2)，作为当前认领挂在任务上，认领的变化另记事件。如果认领需要独立的生命周期，可以改为 (1)。
- **Fact**：谁持有这项任务，以及在哪、用哪个分支、从哪个基线开始、从什么时候起。
- **Authority**：当前认领以台账该行为准；认领的变化（认领、释放、转交）以任务记录里的事件为准（第 16.1 节选定方案二）。
- **Writers**：
  - 认领时，由受控入口代认领的 agent 写；
  - 持有人可提交交接释放申请，main 合入后才生效；
  - 被放弃的认领只能由人释放（需求第 35 节）。
- **Readers**：准备开工或续接的 agent；以后的系统建设页（显示执行人）。
- **Derived Copies**：分支名、PR 描述里的提法、agent 记忆。
- **Freshness**：必须同时看 main 和开着的 PR，区分待合入申请与 main 上的有效认领；分支申请不能授权开工。构建时读不到申请。
- **Conflict Rule**：
  - main 上已有有效认领的，后来者停下；
  - 两个申请都未合入时都不生效；按第 7 节串行确认，第一个有效后，其他申请必须拒绝，不能通过解决文本冲突替换持有人。

### 4.3 checkpoint

- **分类**：(2)，作为任务记录里的一种条目。
- **Fact**：做到哪里、改了哪些文件、证据指向、未解决问题、下一步、当时的基线。
- **Authority**：任务记录（第 16.1 节选定方案二）。
- **Writers**：只有当前认领持有人。
- **Readers**：续接的 agent、操作者；以后的系统建设页（最后一次检查点的时间）。
- **Derived Copies**：PR 描述里的摘要、agent 记忆、聊天。
- **Freshness**：只对它记录的基线有效。main 或分支动了，就要做漂移检查。
- **Conflict Rule**：按已生效的认领历史验证写入资格；前任持有期间留下的检查点继续有效。非持有人写的进展无效，人工恢复报告另记事件；只追加，不覆盖。

### 4.4 handoff

- **分类**：(2)，看作一种特殊的检查点：它多带转交意图和接收角色，并在交接释放控制变更合入后结束写入者的认领。
- **Fact**：交出时的完整状态、下一步、阻塞项、分支和源版本。
- **Authority**：任务记录（第 16.1 节选定方案二）。
- **Writers**：交出认领的持有人。派给谁由操作者决定（第 16.4 节）。
- **Readers**：接手的 agent、操作者。
- **Derived Copies**：今天 PR 描述里的“交接”一节、聊天。
- **Freshness**：在认领转交之前、且没有漂移时有效。
- **Conflict Rule**：认领释放前，交接必须不早于该持有人的最新检查点。释放生效后原持有人不能再追加进展；接手者的检查点必须引用已消费的交接。异常中断按第 11 节人工恢复事件替代缺失的交接，历史都不覆盖。

### 4.5 acceptance

- **分类**：
  - 验收策略（human / automated / hybrid）和验收条件：(2)，是任务契约的字段；
  - 验收结果（谁在什么时候按什么验收了）：(3)，记为 human_approval 类证据。
- **Fact**：这项任务怎样才算验收，以及实际的验收记录。
- **Authority**：
  - 策略和条件：由人决定。验收策略写在任务记录里，验收条件在台账“退出证据”列（第 16.1 节）。
  - 验收记录：沿用台账第 1 节第 4 条的要求：验收人、日期、结论、原话。
- **Writers**：
  - 策略和条件：只能人写；
  - 验收记录：人作出决定，agent 可以转录候选证据；受控入口必须验证第 12 节的可信确认凭据。原话和仓库路径不能单独证明批准真实。
- **Readers**：受控入口（执行 accept 转移时）、CI、操作者。
- **Derived Copies**：验收单、台账行内原话、系统建设页的 `ack:` 证据。
- **Freshness**：验收记录只追加；批准绑定任务契约和候选证据版本，相关内容变化必须重新批准，撤销保留历史；策略改动只能由人来。
- **Conflict Rule**：验收记录与策略不符时，不能进入 done。

### 4.6 human_decision

- **分类**：不在 REV-45 里建成独立域。任务相关的人工决定记为任务的证据 (3)，并引用各自已有的权威：
  - 合并权：登记表；
  - 范围：台账范围变更表；
  - 验收：验收记录；
  - 源表写入批准：F6 审批路径（`AGENTS.md` 第 3 节）。
- **Fact**：谁在什么时候批准了什么、范围多大、何时失效。
- **Authority**：跨领域统一人工决定的权威仍 OPEN。原因是人工决定今天分散在五处，格式各不相同：登记表、范围变更表、验收单、行内原话、JSON 验收记录；统一成一个域是跨领域的改动，超出 REV-45（需求第 38 节：不要重复建设第二套 Agent Approval）。V1 的做法已定（第 16.7 节）：验收人为操作者，批准记成任务记录里的一条结构化证据，并通过第 12 节的独立可信渠道验证。
- **Writers**：人作决定，agent 记录。
- **Readers**：受控入口、CI、续接的 agent（续接第 10 步检查“有没有新的人工决定”）。
- **Derived Copies**：聊天消息（不能是唯一出处，需求第 34 节）。
- **Freshness**：以记录时间为准；有失效条件的（如登记表），按条件判断。
- **Conflict Rule**：决定之间互相矛盾时，由操作者裁定，agent 不自行选。

### 4.7 对来源登记机制的影响

- 如果采用第 5 节方案二，“任务记录”可以作为一个新域登记：权威是任务记录文件，台账仍是状态权威。曾评估以下三项扩展，V1 取舍按第 16.3 节：
  - 能指向一组文件；
  - 能按单条记录的日期判断过期；
  - 能标“只给 agent 用、不上公开页”。
- V1 只需要文件集合支持；另两项暂缓，不作为实施阻塞。

## 5. Proposed Task Contract（需求第 30 节 D）

先说记录放在哪，因为下表的“谁写”取决于它：

- **方案一：都放在台账和 PR 描述里（改动最小）**
  - 认领和审计写成短条目，追加在台账“执行”格；检查点和交接写在任务 PR 描述的固定一节，也就是旧稿的做法。
  - 缺点：
    - 台账格子越来越长；
    - PR 描述不进 git，离线构建读不到，改了没有版本；任务跨几个 PR 时还要搬；
    - 审计混在格子文字里，难以校验。
- **方案二（已选）：台账管状态，任务记录管过程**
  - 台账每行只放状态和当前认领，是唯一权威。
  - 每项任务一份只追加的记录文件，例如 `code-as-doc/dev/tasks/REV-20.yaml`（文件名实施时定），记认领事件、检查点、交接、证据、状态变化事件，照 `publication_actions.json` 的做法由代码校验。
  - 为什么不会形成第二套状态（需求第 22 节）：
    - 记录文件只记“发生过什么”，不记“现在是什么”；
    - CI 要求台账的每次状态变化都有一条对应事件，事件的 from、to 与台账改动前后的值一致；同一 PR 有多次变化时逐条验证完整事件链。纯认领转交允许 from = to，仍须验证旧 claim_id、释放和新认领的顺序。
- **方案三（以后，需求第 24 节）**：事件记录做权威，台账由它生成。现在不做。

## 6. Proposed State Machine（需求第 30 节 E）

状态图。需求给出的主干保持不变，本稿补充的转移放在括号里，由操作者确认：

```text
planned ──(前置满足，算出)──→ ready
  │                            │
  │                        (agent 认领)
  │                            ↓
  │                         claimed ──(开工)──→ in_progress ──→ verifying ──(人验收)──→ done
  │                            │                  │   ↑            │
  │                            │                  │   └──(验收不过)─┘
  │                            │                  ↓
  │                            │               blocked ──(重启条件满足)──→ in_progress
  │                            │
  │             （交接只释放认领、保持状态；重新认领后才能继续）
  ↓
deferred / cancelled（人决定；另见下表）
```

状态转换矩阵：

| From | To | 谁可以执行 | 需要的证据 | 需要的条件 |
| --- | --- | --- | --- | --- |
| （无） | planned | 人；agent 只能提议 | 范围变更表的决定记录（原话、日期） | task_id 唯一（取号工具）；标题、范围、验收条件齐全 |
| planned | ready | 系统算出，不存储（第 16.2 节） | 各前置任务的 done 记录 | 前置依赖都是 done；需要的阶段门已验收 |
| ready | claimed | agent 提交申请；操作者串行确认 | main 上已生效的认领记录（第 7 节） | 没有有效认领；预期状态与认领版本未变；并行的切片数在操作者允许的范围内 |
| claimed | in_progress | 持有人 | 开工检查点（含基线） | 执行者就是持有人；基线已记录 |
| in_progress | blocked | 持有人或人 | 阻塞记录：阻塞点、阻塞的权威、重启条件、下一步、解锁人、复查日期 | 执行者是持有人或人 |
| blocked | in_progress | 持有人（有证据表明重启条件已满足时）或人 | 重启条件已满足的证据 | 同上 |
| in_progress | verifying | 持有人 | 每条验收条件都有对应的退出证据；最新检查点 | 证据齐全；没有未解决的阻塞 |
| verifying | in_progress | 验收人（验收不过），或持有人（自己发现问题） | 验收失败记录，保留不删（需求第 35 节） | 失败记录已写入 |
| verifying | done | human 策略下只能由人；automated 策略下由受控验证器；hybrid 两者都要 | human：验收人、日期、结论或原话；automated：机器检查结果 | 满足验收策略；证据满足验收条件 |
| planned、ready、blocked | deferred | 人 | 决定记录：理由、重启条件 | — |
| planned、ready | cancelled | 人 | 决定记录（出处） | — |

需求表里没有、本稿补充的转移（第 16.2 节已确认）：

| From | To | 谁可以执行 | 说明 |
| --- | --- | --- | --- |
| claimed | ready | 人 | 尚未开工且没有待续接成果时，撤回认领；持久状态回到 planned，ready 按前置条件算出。已有成果用下面的交接规则 |
| deferred | planned 或 ready | 人 | 重启条件满足后 |
| claimed、in_progress、blocked、verifying | cancelled | 人 | 进行中被取消 |
| claimed、in_progress | deferred | 人 | 进行中被暂缓 |
| claimed、verifying | blocked | 持有人或人 | 开工前或验收中受阻 |
| ready | planned | 系统算出 | 前置条件倒退；ready 是算出来的，自动成立 |
| done | — | 不允许 | 验收后发现问题就新开一项任务，引用原任务（第 16.2 节） |

禁止的转移：planned → done、ready → done、claimed → done、blocked → done，以及任何跳过中间状态的转移，例如 REV-44 实际发生过的 planned → verifying。

agent 可以执行的转移：
- ready → claimed；
- claimed → in_progress；
- in_progress ⇄ blocked，前提是有重启证据；
- in_progress → verifying；
- verifying → in_progress，仅限自己发现问题时；
- 提交交接释放申请（main 合入后生效）。

其余都必须由人或受控验证器执行，包括：进入 done、deferred、cancelled；被放弃认领的释放；范围和验收条件的修改。

进行中交接不是进度状态转移。以下列出同状态事件及尚未开工的例外，不能把已完成的工作退回 ready：

| 当前状态 | 事件 | 生效后的状态 / 认领 | 条件 |
| --- | --- | --- | --- |
| in_progress、blocked、verifying | handoff_release | 状态不变；claim 为空 | 当前持有人交接，交接与释放同一控制变更生效；阻塞、待验收证据保留 |
| claimed | handoff_release | claimed → ready，claim 为空 | 尚未开工；交接保留，B 从 ready 重新申请；已有成果先合法进入 in_progress |
| in_progress、blocked、verifying | resume_claim | 状态不变；产生新 claim_id | 操作者派发、旧认领已释放、通过第 11 节校验和第 7 节串行确认 |
| claimed、in_progress、blocked、verifying | human_release | 状态规则同上；claim 为空 | 人工恢复事件记录原因、可用成果和恢复基线；不能假冒原持有人写交接 |

没有有效认领时，任何 Agent 都不能开工、追加进展或写业务数据。blocked 的新持有人仍须提供解阻证据才能回到 in_progress；verifying 的新持有人只能继续验证流程，需要修改成果时先按矩阵退回 in_progress。

## 7. Proposed Claim Model（需求第 13、21、35、40 节）

- **字段**：
  - claim_id：每次认领新生成、不可猜，照构建队列的 `claim_token`；
  - task_id；
  - holder：agent 类型，如 claude、codex、openclaw；
  - where：窗口或主机标签；
  - branch；
  - base_revision：认领时 main 的提交号；
  - claimed_at；
  - claim_status：active 或 released；
  - released_by、released_at、release_reason。
- **为什么需要 claim_id**：认领只写“Claude（桌面窗口）”，分不出是哪个窗口。这次盘点时，子 agent 就把本窗口搁置的分支当成了“另一个窗口的认领”。git 也分不出（第 14 节）。
- **唯一性**：一项任务同时只有一个有效认领，不抢占（需求第 15 节）。
- **申请与生效分开**：分支上的认领是 proposal，只有 main 台账中的 active claim 才授权执行。草稿 PR 只用于发现申请，不是锁；申请允许做只读准备，不能开工或产生业务写入。
- **串行确认点**：V1 由操作者串行处理认领控制 PR，合入前针对最新 main 复核 `expected_status`、`expected_claim_id`（首次为 null）和该任务控制版本。控制版本是台账该行与任务契约/事件前缀的摘要，不因无关任务变化失效。申请还要绑定 holder、目标工作分支、派发依据和唯一 request_id。
- **冲突处理**：两份申请看到同一旧状态时，第一份合入使控制版本变化，第二份必须拒绝；不得靠文本冲突解决覆盖旧持有人。CI 复核同一前置条件；旧 CI 结果不能代替合入时复核。V1 不把该控制 PR 纳入 Agent 自动合并范围，不以 pre-push 或 Git 自动合并充当原子认领。
- **执行前确认**：申请者重新读取 main，确认 task_id、claim_id、holder、控制事件均匹配才进入执行。只有申请 PR 合入不够，还须读回确认。受控入口在每次状态修改和业务动作前重查认领；读不到权威或身份不符就停止。持有人交接释放后立即停止写入，且不得继续使用旧 claim_id。
- **控制与成果分支**：认领/释放/续接的控制 PR 从最新 main 建立，只改台账与任务记录，不夹带未完成的业务成果。任务工作分支单独保存成果。释放申请在合入前不生效，B 必须等 main 读回释放后再申请。合入认领 PR 后删除控制分支不会删除任务工作分支。
- **可见性**：申请后立即开草稿控制 PR，标题带 REV 编号；查询 main 和开着的 PR 用于减少重复申请。生效的认领只有一个；仅靠 PR 搜索不能保证这一点，保证来自以上串行确认和执行闸门。
- **到期、释放、接手**（需求第 35 节）：
  - 第一版不自动超时；
  - 持有人提交交接与释放申请，合入 main 后生效；
  - 被放弃的认领只能由人释放；释放前先确认旧执行者已停止，检查尚在运行的外部操作，未确认静止就不能重新派发；
  - agent 不能接走别人的认领，只能由操作者重新派发；
  - 认领长期没有检查点时，可以作为提示报告给操作者，但不自动处理（第 16.6 节）。
- **与分支和 worktree 的关系**（需求第 40 节）：
  - 认领记录 branch 和 base_revision；
  - 每个检查点记录 current_revision；
  - 这些值直接取自 `openclaw_git_guard.py status`；
  - 推送时照常由 pre-push 守卫把关，它不替代认领确认；
  - V1 保证遵守受控入口的 Agent 之间不会同时获准执行；同一账号下绕过入口的任意 shell 写入无法被文档约束成技术隔离，不能宣称具备这种隔离。

## 8. Proposed Checkpoint Model（需求第 16、35、40 节）

```yaml
checkpoint:
  task_id: REV-20
  claim_id: <当前认领>
  executor: {holder: claude, where: <窗口或主机>}
  created_at: <UTC 时间>
  baseline: {branch: <分支>, head_sha: <提交>, dirty: false, main_sha: <当时的 main>}
  registry_revision: <来源登记文件的提交号>
  completed: [...]
  current_state: [...]      # 做到哪里，不写推理过程
  changed_files: [...]
  evidence: [...]           # 第 9 节的证据条目
  unresolved: [...]
  next_action: [...]
```

- **何时写**：每次停下时（一轮结束、上下文快满、交接前）、每次推送后，以及长任务的阶段边界。
- **规则**：
  - 只追加；
  - 只有持有人能写；
  - 只写下一个执行者需要的事实，不写推理过程；
  - 仓库是公开的，不写凭据和敏感内容。
- **有效性**：只对它的 baseline 有效。续接时要和当前 main、分支对比（第 11 节）。
- **Agent 崩溃时**（需求第 35 节）：
  - 有检查点的，人工释放并记录恢复事件后，从最新可信检查点续接（第 11 节）；
  - 没有检查点的，由人确认最后一条可信证据与恢复基线；没有证据就重新执行。未记录的本地文件先保全，不删除，也不认定为已验收成果。

## 9. Proposed Evidence Model（需求第 17 节）

在系统建设页现有的证据语法（`pr:`、`file:`、`url:`、`rev:`、`ack:`）上补齐类型：

| 类型 | 必填内容 | 今天有没有 |
| --- | --- | --- |
| pr | 仓库、编号、状态、合入提交 | 有（`pr:`） |
| commit | 提交号 | 没有 |
| file | 仓库、路径、所在提交 | 有（`file:`，不带提交号） |
| test | 命令、结果、日志位置（必须持久） | 没有 |
| build | 运行链接、结论 | 没有 |
| artifact | 路径、sha256、保留期限 | 没有 |
| url | https 链接，可在线检查 | 有（`url:`） |
| snapshot | 路径、导出时间 | 没有（来源登记里有快照，但不是证据类型） |
| human_approval | 决定人、日期、决定、原话、范围、持久出处、可信凭据 id、契约/候选证据摘要、撤销信息 | 部分有（`ack:`，但页面规定它不能是唯一证据） |
| external_receipt | 系统、记录 id、字段、值、回读结果 | 没有；写法照 `lark-cli-bitable-ops` 技能的写后回读规矩 |

规则：

- 证据必须能在仓库或稳定链接里找到。会话临时目录、7 天就删的 Actions 产物都不算。
- 只增不删。验收失败的记录也保留（需求第 35 节）。
- “agent 认为已经完成”不是证据。
- 证据只证明任务按定义完成，不证明下游业务事实正确。下游事实是否权威，仍由各自事实域的规则决定（需求第 52 节）。

## 10. Proposed Handoff Contract（需求第 30 节 F）

```yaml
handoff:
  task_id: REV-20
  from: {holder: claude, where: <窗口>, claim_id: <释放的认领>}
  to: {role: <接手角色，或留空由操作者派>}
  created_at: <UTC 时间>
  handoff_id: <唯一记录 id>
  source_revision: {main_sha: <当时的 main>, branch: <成果分支>, work_revision: <交接覆盖的成果提交>}
  control_revision: <提交交接申请前的任务控制版本>
  registry_revision: <来源登记的提交号>
  scope_ref: <交接时任务范围所在的提交>
  completed: [...]
  current_state: [...]
  evidence: [...]
  unresolved: [...]
  blocked_by: [...]
  files_touched: [...]
  next_action: [...]        # 必须具体到下一个动作（需求第 45 节第 7 条）
```

| 问题 | 回答 |
| --- | --- |
| A 在什么时候产生 handoff | 任务没完成、要换执行者时：会话结束、上下文快满、需要别的技能、操作者要求换人 |
| 写在哪里 | 方案二写在任务记录里；方案一写在 PR 描述里（第 5 节，第 16.1 节） |
| 谁是 authority | 交接内容以任务记录为准；状态和认领以台账为准 |
| B 怎样发现它 | 从操作者的派发（点名任务）→ 台账该行 → 任务记录或 PR；认领还没进 main 时，按 REV 编号搜开着的 PR |
| B 怎样确认它仍然有效 | 按第 11 节续接算法逐项核对：源版本、分支、范围、人工决定、认领是否已释放 |
| source revision 变了 | 比较任务范围、契约及依赖权威的实际变化；预期的认领/交接控制事件单独验证，不当作业务漂移。无关变更记录“已检查，无影响”；相关变更停止并对齐 |
| branch 变了 | 验证 work_revision 存在且是成果分支当前 HEAD 的祖先；其后只能有经校验的记录追加或预期控制同步，任务成果及依赖内容必须不变。无法证明、分支删除或历史改写就停下报告 |
| task scope 变了 | 台账该行的范围或验收条件在交接之后改过，交接中受影响的部分就失效，停下问操作者 |
| human decision 变了 | 只检查与本任务范围及依赖有关的新决定；预期的释放与派发单独校验，其余改变范围、证据或授权的决定需要对齐 |
| 能否覆盖 | 不能。只追加，新的一条取代旧的，旧的保留 |
| 历史是否保留 | 保留（任务记录只追加，另有 git 历史） |

**版本锚点**：work_revision 固定为写交接前的成果提交，不尝试把包含交接记录自身的 commit SHA 写进记录。记录所在提交由读取者按 handoff_id 在 git 历史中解析。检查点的 baseline.head_sha 同样指被描述的成果基线。后续差异按路径和语义校验：只追加记录不能改变契约、现有证据或审批；不能因为某个文件名属于 tasks 目录就跳过其内容校验。控制 PR 合入产生的 main 变化不自动构成成果漂移。

命名：仓库里的 handoff 已经指 IDML 交付包（`tools/idml/design_handoff.py`、`*_handoff.zip`，已复核）。任务交接叫“交接记录”，文件名避开 handoff。

## 11. Resume Algorithm（需求第 30 节 G）

B 只接受操作者的派发作为输入。派发只需点名任务，不需要复述进展。

1. **读任务契约**：台账该行，以及任务记录。
2. **读来源登记**：只读 authority_dependencies 列出的域。
3. **核对任务状态**：允许 ready（尚未开工交接或人工恢复）、in_progress、blocked、verifying；旧认领必须已在 main 释放。claimed 仍有有效持有人时不得接手。
4. **核对前置条件**：仍然全是 done。
5. **核对认领**：main 没有有效认领；查看开着的申请并交由操作者串行处理，不能把查询结果当成锁。
6. **读最新可信检查点**；缺失时使用人工恢复事件指定的证据与基线，不要求伪造检查点。
7. **读最新交接**：正常路径必须来自最后一任持有人，并且不早于该持有人的最新检查点。崩溃无交接时，必须存在操作者批准的恢复事件，记录旧 claim_id、释放原因、可信检查点/证据引用、源版本、工作分支、work_revision、阻塞项与 next_action；它代替交接，不能伪造前任交接。没有可信基线则停下等待人工决定。
8. **核对源版本**：交接或人工恢复事件里的 main_sha 对比现在的 main，registry_revision 对比现在的来源登记，只看任务路径和依赖权威上的变化。
9. **核对分支和工作区**：按第 10 节验证 work_revision 的祖先关系及后续差异；用 `openclaw_git_guard.py status` 查工作区；推送前包含最新 main。
10. **查新的人工决定**：交接或人工恢复事件之后，与本任务有关的范围变更、验收、登记表授权和 PR 评审；预期的释放/派发单独验证，不重复触发阻塞。
11. **查阻塞项**：交接、检查点或人工恢复事件里的 unresolved、blocked_by。
12. **认领**：经受控入口提交 resume_claim（ready 用首次 claim）；按第 7 节等待串行合入，读回确认持有人与版本后才能继续。等待期间契约、成果或批准变化须重跑校验。
13. **写一条续接检查点**：记下第 3–11 步各查了什么、结果如何。
14. **续接**：只用最小上下文，即任务契约、适用的 `AGENTS.md`（按任务范围里的路径找）、相关技能、登记引用、检查点、交接、证据（需求第 41、42 节）。

任何一步发现漂移，都按同一个顺序处理：停下 → 写候选校验失败报告（尚未认领者不得写持有人检查点或直接改状态）→ 由操作者或对应权威对齐 → 从第 1 步重新开始。不自动猜，也不“先做再说”。

## 12. Acceptance Model（需求第 8、18、34、35 节）

- **human（第一版全部用它）**：agent 最多提交到 verifying。verifying → done 必须有人工批准证据，内容包括验收人、日期、结论、原话和出处；出处必须持久保存，且通过下述可信来源验证；仅将聊天原话抄进仓库不算通过。
- **automated**：只用于验收条件完全能由机器判断的任务，例如测试通过、schema 合法、哈希一致、产物存在、没有意外差异，由操作者逐项指定；第一版不开。
- **hybrid**：机器检查通过，再加人工决定。
- **验收不过**：verifying → in_progress，失败记录保留，不能删掉失败记录后重交（需求第 35 节）。
- **Human Authority 负责的事**（需求第 34 节）：
  - 任务范围、验收条件；
  - 高风险的源数据改动；
  - 机器判断不了的内容质量；
  - 合规和法务等业务决定；
  - 架构范围的变更；
  - 需要人工验收的 verifying → done；
  - agent 解决不了的权威冲突。
- **合并授权不是验收**：gate-on-green 授权的是合并，不是 done。台账第 1 节第 4 条写明“代码合入或 CI 绿不能代替”。
- **done 不等于下游事实正确**：REV-xx = done 只代表这项任务按定义完成并通过验收（需求第 52 节）。

### 12.1 人工批准的可信来源与执行闸门

- **区分转录与确认**：Agent 可提交 human_approval 候选记录，但填写 actor=human、姓名、原话、链接都不赋予权限。CI 只能检查结构与绑定，不能从这些自述字段推断人已批准。
- **可信来源**：沿用人工验收语义，批准必须由操作者通过 Agent 无法使用其批准凭据的渠道确认，例如仅操作者持钥的签名回执，或独立身份的认证审批服务返回的可验证回执。凭据标识、验证材料和撤销状态可供受控入口读取；签发私钥/批准权限不能暴露给 Agent。仓库共用 GitHub 账号的评论、提交或合并不能单独作为可信人类身份。
- **绑定**：凭据至少绑定 task_id、decision_id、accept/reject、验收人身份、任务契约摘要（scope、acceptance_criteria、policy）、候选成果与 evidence_set 摘要、签发时间。候选证据不包含批准回执本身或后续纯审计事件，避免自引用。决定重复投递按 decision_id 幂等；相关内容改变、凭据撤销或失效时必须重新验收，旧记录只追加保留。
- **进入 done**：受控入口针对最新 main 验证凭据、授权验收人、契约和证据绑定，再提交 accept 控制变更；合入前重新核验。验收相关内容变化使原结果失效；无关记录追加不使批准失效。合并授权不能替代该核验。
- **实施前置条件**：当前盘点只证明共用账号和人工原话记录存在，没有证明上述独立渠道已经可用。V1 实施前必须选定并验证渠道及凭据隔离；未完成则保持 verifying，报告 `human_approval_unverifiable`，不能退化为信任 Agent 转录，也不能宣称“无法伪造人工批准”已通过验收。本稿不建立第二套业务审批权威，仅规定既有人工决定如何被验证。
- **权限边界**：防伪保证限定于批准信号与受控入口；若 Agent 还能任意修改验证器、可信密钥配置或绕过受保护合入规则，保证不成立。这些治理配置必须由操作者控制，实施验收需要证明执行身份无此权限。

## 13. Concurrency Boundary（需求第 21、31 节）

第一版做：

- 一项任务只有一个有效认领（第 7 节）。
- 仓库里的权威文件只经 PR 修改：
  - 推送前必须包含最新 main（pre-push 守卫）；
  - 认领控制 PR 由操作者串行确认，按最新 main 校验前置状态（第 7 节）；
  - 文本冲突只是一种提示，不能证明唯一性；必须验证任务控制版本，后续申请不得覆盖已生效认领。
- 同时进行的切片数由操作者决定（台账第 1 节第 3 条）。
- 飞书线上表只在操作者批准后写，写后回读（`AGENTS.md` 第 3 节）。

第一版不做：资源锁、分布式锁、自动超时、调度（需求第 21、31 节）。构建队列的租约和并发组保持原样，只管构建。

## 16. 历史设计选择与理由（当前不实施）

### 16.1 任务状态的权威，以及过程记录放在哪（需求第 50 节点名）

**定了什么**：
- (a) REV 任务的“当前状态”以哪里为准；
- (b) 认领、检查点、交接、证据、状态变化事件这些过程记录放在哪里。

**为什么当时要定**：后面每一部分都建在这上面。状态如果存了两处，就会分叉（需求第 6 节）。

**选项**：
- 方案一：认领和审计追加在台账格子里，检查点和交接写在 PR 描述里；
- 方案二：台账管状态，每项任务一份只追加的记录文件管过程；
- 方案三：事件记录做权威，台账由它生成。

详见第 5 节。

**决定**：(a) 台账是 REV 任务状态的唯一权威；(b) 选方案二。

**理由**：
- 台账已经在当权威用：第 6 行自称“唯一执行状态入口”，来源登记和系统建设页都读它，不需要迁移。
- PR 描述不适合放检查点和交接：它不进 git，离线构建读不到，改了没有版本，任务跨几个 PR 时还要搬。
- 方案二的记录文件只记“发生过什么”，“现在是什么”仍只看台账；CI 校验两边一致，所以不会形成第二套状态。
- 方案三要把台账改成生成出来的文件，改动大，等方案二用出真实需要再说（需求第 24 节）。

### 16.2 状态机（需求第 50 节点名）

分四小项。

**(a) 台账的 active 是否拆成 claimed 和 in_progress。**
- 决定：拆，并采用需求第 9 节的九个状态，同时改台账第 1 节第 4 条。
- 理由：
  - “已认领未开工”和“已开工”今天都写成 planned（REV-39、REV-45），拆开才分得清；
  - 台账里从没有一行用过 active（已复核），改规则不用迁移数据。

**(b) ready 是存下来，还是读取时算出。**
- 决定：算出，不存。
- 理由：前置依赖或阶段门条件改变时，存下来的 ready 会悄悄过期，算出来的始终和台账一致。
- 代价：planned → ready 不再是一条事件，改在认领事件里记下“认领时前置已满足”。事件 from/to 使用台账持久值，首次认领记录 planned → claimed；effective_from=ready 及前置证据单列。释放到 ready 则持久写 planned，不在台账另存 ready。

**(c) 第 6 节补充的转移。**
- 决定：采用第 6 节补充表；2026-09-26 审核修订将交接释放改为保持进度状态的事件，仅尚未开工的 claimed 撤回到 ready。执行者权限按修订后的表执行。
- 理由：这些情况今天真实发生过，或者规则里已经隐含。例如台账要求 deferred 写重启条件，却没有“重启”这条转移。

**(d) done 之后发现问题怎么办。**
- 决定：不重开原任务，新开一项并引用原任务。
- 理由：原任务的验收证据保持有效，审计记录不被改写；新问题有自己的范围和验收条件。

**(b) 方案二的任务记录要不要登记为新域。**

### 16.4 交接格式（需求第 50 节点名）

## 17. 与现有机制的关系（需求第 32–42 节）

### 17.1 Agent 可替换（需求第 33 节）

- 任务契约、任务记录、状态机、证据都与具体 agent 无关；holder 字段只记类型，不决定权限。
- `AGENTS.md` 已经是 Claude 和 Codex 共用的唯一规则源（根 `AGENTS.md` 开头、`CLAUDE.md` 用 `@AGENTS.md` 引入）。
- 有两个技能在 `.claude/skills/` 和 `.agents/skills/` 各有一份：hardcore-task-execution、config-review（`AGENTS.md` 第 7 节）。两份会漂移，属于“同一套技能”的风险，记为后续事项，不在 REV-45 处理。

### 17.2 治理不能被绕过（需求第 37、38 节）

- **原则**：Orchestration does not imply authorization。REV-45 的受控入口只管任务状态，不授予任何业务权限。
- **照旧生效的关口**：
  - 合并授权（登记表）；
  - 分支规则（pre-push 守卫、分支保护）；
  - 飞书写入批准与回读（`AGENTS.md` 第 3 节）；
  - 资产关卡；
  - 评审和回写的审批（云文档回写只写 review 派生物，源表走 F6）；
  - 发布确认（`queue-execute` 的 `--confirm-publish`）；
  - 人工决定。
- **合并授权属于治理决定**：它回答“谁可以合并什么、范围多大、何时失效”。任务把用到的 MA 编号记为证据（例如“本 PR 按 MA-nnn 合入”），不另建一套 Agent 审批。它也不等于验收（第 12 节）。

### 17.3 Task 与 Queue Item（需求第 39 节）

- **语义不同**：
  - Task 是工程或业务工作单元，权威在台账；
  - Queue Item 是一次执行请求，权威在飞书构建表的行，有自己的状态机和租约（`code-as-doc/dev/queue_state_model.md`）。
- **一对多**：一个任务可以产生多个队列项。例如“发布某目标某版本”会依次产生构建、发布和回执。任务把每个队列项的记录 id、结果和回读记为证据。
- **不拿队列状态当任务状态**：队列行的 SUCCESS 只说明这次执行成功，不等于任务完成。

### 17.4 系统建设页（需求第 26、36 节）

- 页面只做读模型，不做控制台，不加按钮。
- 现在手写的任务事实（`now_labels`、`rev:` 状态钉、进度文字）是第二套状态的来源。建议实施阶段把“当前在做”改为由台账状态算出，即 claimed、in_progress、verifying、blocked 的行；页面状态词表跟着第 6 节一起改。
- 本稿不改页面。

### 17.5 上下文与目录级 AGENTS.md（需求第 41、42 节）

- **执行路径**：Task → 任务范围里的目标路径 → 适用的 `AGENTS.md`（根目录一份，加上路径所在目录的那份）→ 相关技能 → 执行。
- 任务契约不复制目录规则。
- 续接只读第 11 节第 14 步列出的最小集合，不读整个仓库。

### 17.6 不重构现有生产能力（需求第 32 节）

- 构建、发布、TM、回写、资产的技能和工具原样调用。
- REV-45 只回答三件事：哪个 agent、在什么任务状态下、什么时候调用这些能力，以及调用之后怎样记录结果。

| A、B 同时从无认领状态提交申请 | 合入前两者均不能执行；A 生效后 B 旧控制版本被拒绝，即使文本冲突已手工消除 |
| A 正常交接正在进行的任务 | 交接和释放原子生效，状态保持 in_progress；B 新认领生效并复核成果后才能追加检查点 |
| blocked / verifying 状态交接 | 阻塞或待验收状态与证据保持；重新认领本身不解阻，也不代表验收通过 |
| A 崩溃，没有交接或没有检查点 | 人工恢复事件确认释放与可信基线；B 不伪造交接、不删除未知本地成果；无可信基线停止 |
| 写入交接记录后提交、合入控制 PR | work_revision 不变，合法记录追加可通过；业务成果改变、契约变化或历史改写被拒绝 |
| Agent 填写虚构批准或复用旧批准 | 无可信凭据、错误任务、改变契约/证据、撤销凭据均不能进入 done；同一决定重复投递不重复执行 |
| 使用共用账号自行发布“批准” | 不能通过身份验证；独立确认渠道未就绪时明确阻塞，不能以 CI 绿代替人工验收 |
| 验证后、合入前发生相关变化 | 认领前置版本或验收绑定失效，必须重新验证；无关任务更新不使本任务协议失效 |

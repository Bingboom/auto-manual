## 要点

1. 任务状态今天已经有事实上的权威，就是执行台账：来源登记里的 `ledger` 域指向它，系统建设页也按它显示进度。缺的不是再登记一个权威，而是结构（认领、时间、状态变化记录）和受控写入。
2. 台账规则定义了 7 种状态，实际只用过 4 种，从没用过 active、blocked、cancelled，系统建设页也只认这 4 种。已开工的任务仍标 planned（REV-39、REV-45），REV-44 从 planned 直接跳到 verifying。
3. 第二套状态已经出现：
   - 系统建设页有手写的“当前在做”清单，以及手抄的状态钉和进度文字；
   - 台账自己也在漂移：REV-07 行、文件头状态；
   - 合并授权登记表的 MA-171、MA-172 也没翻。
4. 仓库里已有可以照搬的做法：
   - 构建队列的认领租约：令牌、到期、回读；
   - 网页下架与恢复的事件账本：状态由事件重放得出，非法转移报错，必须写明操作者、原因、时间。
5. 缺的：结构化认领、检查点、交接、更新时间、状态变化记录。另外，git 分不出是哪个 agent 做的，两个仓库也都是公开的。
6. 建议第一版的做法（第 4.8 节方案二，待操作者定）：
   - 台账继续做状态权威，所有状态变化只经一个受控入口，CI 按同一套规则校验台账改动；
   - 认领、检查点、交接和状态变化事件放在每项任务一份只追加的记录里。

## 3. 状态模型（需求第 9、10 节）

### 3.1 与台账现有状态对照

| 需求里的状态 | 台账现有 | 建议 |
| --- | --- | --- |
| planned | planned | 不变 |
| ready | 无 | 不存储，读取时由前置依赖和阶段门算出（依赖行都是 done、门已验收）。存下来的话，依赖被重开时它会悄悄过期 |
| claimed、in_progress | 合起来是 active | 把台账第 4 条的 active 拆成这两个；要改台账规则，由操作者定 |
| blocked | blocked（定义了，没用过） | 不变；必填字段合并需求第 9 节（阻塞点、阻塞权威、重启条件、下一步）和台账第 5 条（解锁人、复查日期） |
| verifying | verifying | 不变 |
| done | done | 不变；条件是台账第 4 条加上验收策略 |
| deferred | deferred | 不变；理由和重启条件今天写在表下，建议移进行内 |
| cancelled | cancelled（没用过） | 不变；必须写明决定来源 |

### 3.2 转移表没覆盖的情况

需求第 10 节列的转移之外，下面这些情况今天会发生：

| 情况 | 缺的转移 | 为什么会发生 |
| --- | --- | --- |
| 执行者放弃，或认领过期 | claimed → ready、in_progress → ready | 窗口关了、上下文用完、换人 |
| 暂缓后重启 | deferred → planned 或 deferred → ready | 台账第 5 条要求 deferred 写重启条件，条件满足后要能回来 |
| 进行中被取消 | claimed、in_progress、blocked、verifying → cancelled | 操作者改范围 |
| 开工前或验收中受阻 | claimed → blocked、verifying → blocked | 依赖的外部事件没来、验收人不在 |
| 进行中被暂缓 | claimed、in_progress → deferred | 操作者调整优先级 |
| 前置条件倒退 | ready → planned | 依赖项被重开（ready 若按 3.1 算出，这条自动成立） |
| 验收后发现问题 | done → ? | 重开原任务还是新开一项，需要定 |

### 3.3 认领不是状态

- 交接时认领从 A 转到 B，状态可以一直是 in_progress。
- 建议把认领做成单独的字段，记录当前持有者；认领自己的变化（认领、释放、转交、过期）另记事件。
- 这样需求第 10 节的 ready → claimed 由“认领”事件带动，claimed → ready 由“释放”或“过期”事件带动。

### 4.2 认领（需求第 13、21 节）

- **字段**：
  - task_id；
  - claim_id：每次认领新生成、不可猜，照构建队列的 `claim_token`；
  - claimed_by：agent 类型，如 claude、codex；
  - where：窗口或主机标签；
  - branch、claimed_at、expires_at。
- **为什么需要 claim_id**：认领只写“Claude（桌面窗口）”，分不出是哪个窗口。这次盘点时，子 agent 就把本窗口搁置的分支当成了“另一个窗口的认领”。
- **一项任务同时只有一个有效认领**：
  - 不抢占（需求第 15 节）；
  - 过期的认领也不由别的 agent 自动接走，由操作者重新派发；
  - 过期时长是否沿用旧稿定的 7 天，待定。
- **认领进 main 之前只在开着的 PR 上**，所以受控入口在认领前要查 main 和所有开着的 PR（取号工具查编号已经是这样做的）。能保证的和不能保证的：
  - 能保证“只有一个认领合入 main”：两个 PR 改同一行会冲突，后合的必须重做；
  - 不能保证“没人重复开工”，这一点只能靠认领前那次查询。

### 4.3 检查点与交接（需求第 16、19 节）

- **字段**：按需求第 16、19 节，另加两项：
  - baseline：`openclaw_git_guard.py status` 输出的 branch、head_sha、dirty；
  - registry_revision：当时读到的来源登记的提交号，供续接第 5 项检查用。
- **只存事实**：存下一个执行者继续工作需要的事实，不存推理过程。仓库是公开的，不写凭据和敏感内容。
- **命名**：仓库里的 handoff 已经指 IDML 交付包（`tools/idml/design_handoff.py`、`*_handoff.zip`，已复核）。任务交接叫“交接记录”，文件名避开 handoff。
- **放在哪**：见 4.8。

### 4.4 证据（需求第 17 节）

- **格式**：沿用系统建设页已有的证据语法（`pr:`、`file:`、`url:`、`rev:`、`ack:`），再补六类：
  - commit；
  - test：命令加结果；
  - build：运行链接；
  - artifact：路径加哈希；
  - snapshot；
  - receipt：飞书 record_id、字段和回读结果，照 `lark-cli-bitable-ops` 的回读规矩。
- **存放**：证据必须能在仓库或稳定链接里找到。会话临时目录、7 天就删的 Actions 产物都不算——盘点发现有些原始证据只留在临时目录。
- **限制**：“Agent 认为已经完成”不算证据；证据只增不删（需求第 15 节）。

### 4.5 验收策略（需求第 8、18 节）

- **human（默认）**：agent 最多提交到 verifying。verifying → done 必须有人工批准证据：验收人、日期、原话，写法沿用台账第 4 条和现有验收单。
- **automated**：只用于验收条件完全能由机器判断的任务，由操作者逐项指定；第一版不开。
- **hybrid**：机器检查通过，再加人工决定。
- **合并授权不等于验收**：gate-on-green 授权的是合并，不是 done。台账第 4 条写明“代码合入或 CI 绿不能代替”。

### 4.6 受控入口（需求第 23 节）

- **概念命令**，名称到实施时再定：
  - status：只读；
  - claim、checkpoint、evidence、block、handoff；
  - submit：进入 verifying；
  - accept：进入 done，只接受人工批准证据。
- **入口负责**：状态机、前置依赖、认领归属、证据格式、时间戳、执行者、验收策略、审计事件。
- **第一版**：仍以 Markdown 台账为权威。入口改台账行并追加事件，改动照常走 PR。
- **CI 复核**：同一套规则在 CI 里对每个改台账的 PR 再跑一遍，检查四件事：
  - 状态转移合法；
  - done 带人工验收证据；
  - 范围和验收条件没被 agent 改；
  - 证据只增不删。

  这样操作者手改和 agent 改都过同一套检查，不靠 agent 自觉。检查可以挂在现有的 `python -m unittest` 或 `rtd_system_workspace.py check` 里，不必改 workflow。

### 4.7 审计（需求第 25 节）

- **事件字段**：每次状态变化记一个事件，包含 task_id、actor、actor_type（agent 或 human）、from、to、at、reason、evidence、claim_id。
- **执行者必须显式写**：git 分不出是谁（见 1.6）。
- **人的决定也记成事件**：验收、范围变更、取消、重新派发。

### 4.8 记录放在哪（待操作者定）

**方案一：都放在台账和 PR 描述里（改动最小）**

- 认领和审计作为短条目，追加在台账“执行”格里；检查点和交接写在任务 PR 描述的固定一节里（旧稿的做法）。
- 优点：不新增文件。
- 缺点：
  - 台账格子越来越长；
  - PR 描述不进 git，离线构建读不到，改了没有版本；任务跨几个 PR 时还要搬；
  - 审计混在格子文字里，很难校验。

**方案二（建议）：台账管状态，任务记录管过程**

- 台账每行只放状态和当前认领，是唯一权威。
- 每项任务一份只追加的记录文件，例如 `code-as-doc/dev/tasks/REV-45.yaml`（名字实施时定），里面记认领事件、检查点、交接、证据、状态变化事件，照 `publication_actions.json` 的做法由代码校验。
- 为什么不会形成第二套状态（需求第 22 节）：
  - 记录文件只记“发生过什么”，不记“现在是什么”，当前状态只有台账一处；
  - CI 要求台账的每次状态变化都有一条对应事件，事件的 from、to 要和台账改动前后的值一致，两边不会分叉。
- 优点：进 git，离线可读，可以跨 PR，审计可以校验。
- 缺点：多一类文件；需要受控入口才好写。

**方案三（以后再说，需求第 24 节）**：事件记录做权威，台账由记录生成。现在不做，等方案二用出真实需要再说。

### 4.9 续接（需求第 20 节）

| # | 续接前要确认的事 | 今天从哪里能读到 | 缺什么 |
| --- | --- | --- | --- |
| 1 | 任务仍然存在 | main 上的台账行；还没进 main 的认领在开着的 PR 里 | 没有统一查询，要自己搜 PR |
| 2 | 状态允许继续 | 台账状态格 | 没有转移表可以对照 |
| 3 | 前置条件仍满足 | 台账“前置依赖”列、各依赖行的状态、第 3 节阶段门 | 要人工逐项核 |
| 4 | 认领合法 | 台账“执行”格里的认领文字 | 认领没有结构，过期规则只写在被搁置的旧稿里 |
| 5 | 权威有没有变 | 来源登记 `source_registry.yaml` 的 git 历史 | 检查点没记当时读的是哪一版登记 |
| 6 | 源版本有没有变 | 交接或 PR 里写的基线提交，和 main 对比 | 基线是自由文字，不是字段 |
| 7 | 检查点是否仍适用 | 分支上的文件和检查点列出的改动文件对比 | 检查点没有“改动文件”字段 |
| 8 | 有没有新的人工决定 | 台账范围变更表、验收单、合并授权登记表、PR 评论 | 分散在四处，没法按“某时以来”查 |
| 9 | 有没有未解决的阻塞 | 台账 blocked 行的阻塞字段、交接里的失败点 | 交接是自由文字 |
| 10 | 分支和工作区是否安全 | `git status`、`git worktree list`、pre-push 钩子、`AGENTS.md` 第 8.1 节 | 已有，但要执行者自己跑 |

发现漂移时，按需求第 20 节的顺序处理：先暂停，报告漂移，对齐后再续接。

### 4.10 并发（需求第 21 节）

- 一项任务只有一个有效认领（4.2）。
- 仓库里的权威文件只经 PR 修改：
  - 推送前必须包含最新 main（pre-push 钩子）；
  - 合入顺序由 GitHub 决定；
  - 台账同一行被两个 PR 同时改会冲突，后合的必须按 main 重做，并重跑校验。
- 飞书线上表只在操作者批准后才写，写后回读（`AGENTS.md` 第 3 节）。
- 资源锁（需求第 21 节后半）第一版不做。

### 4.11 系统建设页（需求第 26 节）

- 只做读模型，不做控制台，不加按钮。
- 现在手写的任务事实（`now_labels`、`rev:` 状态钉、进度文字）是第二套状态的来源。建议以后把“当前在做”改为由台账状态算出（claimed、in_progress、verifying、blocked 的行）；不在本稿实施。
- 页面的状态词表要和台账状态模型一起改，放在实施阶段。

### 4.12 与 REV-39 的边界（需求第 27 节）

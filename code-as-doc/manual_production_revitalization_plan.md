## 一、目标与取舍

以现有说明书生产系统为基础，优先完成存量网页交付、可靠更新和持续维护，逐步提高多语言及多格式复用能力。Web 先形成业务价值；IDML 按代表产品族并行验证。

未来 90 天的核心目标是：说明书更新能稳定发布、发布事实自动登记、问题能够追溯、人工重复操作减少。访问统计为内容改进提供证据，不作为全系统唯一的优先级依据。

坚持以下约束：

- 业务交付持续进行，平台改造按小批次实施，每批可单独验证和回退。
- 优先复用已有 Web Publish、共享 IR、组件、审核和发布机制；先核实缺口，再补功能。
- 不新建平行 CMS，不为架构完整而拆微服务，不重写现有输出栈。
- 发布产物目录保持纯粹；运营数据、分析报表和人工待办独立维护。
- 组合项目不纳入当前存量网页化范围；扩展范围需单独决定。

## 三、整体架构：双平面、双接入、共享 IR、运营反馈

### 3.1 双平面保持稳定

| 实体 | 职责 |
|---|---|
| auto-manual | 工程主仓库，承载代码、配置契约、测试与架构演进 |
| Hello-Docs | 业务运行与发布镜像，接收工程代码；不在这里发展另一套代码 |
| 业务飞书数据 | 管理经治理的内容、产品参数和业务状态 |
| TM-B | 共享翻译记忆的规范库；不是所有源文案、审核稿和发布译文的唯一存放位置 |
| 说明书运营表 | 展示发布目录与统计，维护负责人、问题和行动，不充当构建源或发布事实源 |

工程侧旧 Base 已存在只读约束，不能笼统规划为可随意写入的试验田。结构演进应使用明确可写的工程环境，经验证和授权后再迁移业务环境。

### 3.2 两种接入方式

**结构化生产路径**：业务内容与参数 → 冻结快照 → 结构装配 → 共享 IR。

**存量接入路径**：现行批准的 AI/PDF → 提取内容与插图 → 整理结构及来源 → 人工确认 → 冻结输入 → 共享 IR。

存量接入允许逐步治理，不要求先把全文录入多维表才能网页化。同一目标应声明当前权威来源、来源版本及接入方式，避免 PDF、模板、表格各自修改而失去一致性。

### 3.3 五层生产职责与运营反馈

| 层 | 职责 | 主要输出 |
|---|---|---|
| ① 内容治理与接入 | 管理内容、参数、资产、语言、区域适用性及来源 | 已确认内容与来源记录 |
| ② 冻结快照 | 冻结构建所需数据、结构、资产和配置 | 可复现输入包、版本与哈希 |
| ③ 结构装配与共享 IR | 组织章节、语义组件和资产引用，解析目标契约 | 渲染器中立的文档结构 |
| ④ 多格式渲染 | 分别处理 Web 响应式布局和 PDF/IDML 固定页面排版 | 各格式候选交付物与验证结果 |
| ⑤ 审核、发布与追溯 | 评审、批准、部署、验证、归档和回退 | 发布记录、部署证据、交付包 |
| 横向：运营与反馈 | 采集使用数据、复核问题、安排修订、验证改进 | 运营行动及修订需求 |

以上沿用架构文档的五层生产模型。运营与反馈是跨层闭环，不新增一套构建层级或发布事实源。

主流程：内容接入 → 快照 → 装配与 IR → 渲染 → 审核发布 → 分发与运营。

反馈流程：问题或使用证据 → 人工判断 → 修订任务 → 正确编辑面 → 审核 → 新版发布 → 效果复核。

IR 共享的是语义、组件实例和资产引用，不承诺各格式像素一致或自动分页一致。通过适配接口测试与通过交付排版验收是两种不同证据。

### 3.4 输出及托管边界

- Read the Docs：提供现有 Web 托管；HT-Doc 为本轮入口整合目标。已选正式域名 `manuals.jackery.com` 的绑定仍依赖 IT/DNS 交接，见[域名操作指南](dev/rtd_custom_domain_runbook.md)。更换托管供应商需另行决策。
- 独立 Web 包：可部署到约定目录；资源、语言相对链接及直接进入各语言页面的行为需验证。
- OSS：承担约定的归档交付；公网外链及正式域名由 IT 管理。归档成功不等于公网可访问。
- PDF/IDML：按格式分别验收。IDML 从代表产品族扩大覆盖，不阻塞已有 Web 交付。

### 3.5 发布出口与旧入口整合

队列 Web Publish / 授权 Git-only → 共享组装与候选验证 → 仅含 `docs/publish/**` 的
Hello-Docs 发布 PR → 合入 `main` → HT-Doc 部署 → 线上版本与链接核验。
两种接入方式保留各自的来源和回执，不为 Git-only 补造队列历史，也不因为共用出口而授权在线表写入。

HT-Manuals 兼容迁移是本轮首批任务，操作及证据要求由
[发布入口整合检查](dev/web_publish_pipeline.md#31-hosting-convergence-and-legacy-entry-review)维护：

1. 逐条建立旧 URL、新 URL、文档身份、内容版本、发布标识和处理结论的对应表。
2. 只读核查 `HTML_link`、包材二维码、历史交付记录；经授权修改时保留原值并回读同一记录。
3. 区分“最新版稳定入口”和“绑定历史版本的链接”。前者可更新映射，后者保留版本语义或给出明确的历史版本说明，不能批量静默指向最新版。
4. 在现有托管能力范围内验证重定向或兼容页、图片、语言入口、下载及移动端；无法迁移的链接明确记录例外、负责人和后续动作。
5. 兼容验证并获发布批准后，停止旧 RTD 项目独立更新；旧入口继续提供兼容服务。
   **这不等于删除 `Hello-Docs/publish` 分支**，该分支仍承担候选快照职责。
6. 两种路径都核对目标站点、实际部署提交与发布标识。站点不符阻止登记为统一入口已验收；迁移故障恢复原映射和可用快照。

本轮入口整合不以正式域名上线为前置，但必须保留未来迁往组织可控制入口的对应记录。

## 四、插图与原生内容规则

1. Web 允许使用从现行 PDF 提取的带标注整图，保留设备、引线及图内说明的完整关系。
2. 章节和小节标题保留为原生结构，整图不包含标题；多个视图并排时应明确一张图覆盖的语义范围，避免标题重复或误归属。
3. WARNING、CAUTION、NOTE、NOTES、正文和说明表格保持原生组件，不因裁图方便整块栅格化。
4. LCD 使用设备图及必要标注配合原生说明表，不把表格变为截图。
5. 整图替换时同步处理被覆盖的旧图和重复文案，检查边框完整、邻区残线、语言匹配、清晰度及移动端效果。
6. 资产裁剪、来源页与区域、配方、注册记录、哈希和目标引用保持一致。
7. 去文字化是多语言复用或特定输出需要时的选择，不把所有带字插图列为待修缺陷。优先处理错语言、重复、截断和不可读问题。

## 五、发布事实、元数据与对账

### 5.1 发布状态分开记录

建议记录：候选已构建 → 审核通过 → 发布 PR 已合入 → 部署成功 → 线上验证通过。

另行记录归档成功、目录同步成功，以及部署失败、同步待重试、已回退、已撤回等状态。沿用现有状态模型并补足证据字段，避免另造互相矛盾的状态机。

PR 合入证明发布候选被接受；RTD 构建成功证明部署流程完成；线上内容核验才证明用户实际访问到目标版本。三种时间分别保留。

### 5.2 核心元数据

优先复用现有 Document_key 和发布身份；字段不足时再扩展，不另建竞争性主键。

| 对象 | 最小信息 |
|---|---|
| 文档身份 | 型号、区域、语言、文档类型、语言范围；与现有文档键映射 |
| 来源 | 接入方式、权威来源版本、快照与资产哈希、内容提交 |
| 发布 | 发布标识、内容版本、构建时间、批准记录、部署标识及时间、验证结果 |
| 交付 | 格式、正文地址、稳定入口、包或归档位置、产物哈希 |
| 运营 | 统计窗口、采集来源、过滤口径、采样说明、负责人及行动 |

当前版本与历史发布分开保存。当前目录不能覆盖历史发布记录，也不能用于猜测历史流量对应版本。

### 5.3 对账与自动登记

- **M0 存量对账**：先建立 HT-Manuals / HT-Doc 的入口与版本对应表，再对齐冻结发布记录、线上部署、成品目录及适用的队列回执。逐项识别缺失、重复、状态不符和版本不符。
- **M1 持续核对**：与 M0、M2 同期建设；新差异告警，已知历史差异记录负责人和处理结论，避免反复报警。
- **M2 自动登记**：先确认现存登记能力和真实缺口，在批准的目标表及字段范围内按发布标识幂等更新机器字段。Git-only 在线目录登记须作为单独获批的后置事务，不改变其不写队列/源表的发布契约。部署失败不可登记为线上可用；目录写入失败进入重试，不能重发整本说明书。
- **M3 装配声明检查**：区分业务勾选、冻结快照与配置能力声明的职责，按适用契约检查，不要求不同语义字段机械相等。
- **M4 稳定入口管理**：复用现有根别名机制，补齐跨站历史链接映射及变更记录；区分最新版入口与历史版本入口，保护已印二维码。别名可读性是辅助规则。
- **M5 统计口径版本**：每期保存窗口、来源、过滤和路径归类规则、采样情况及目录快照。

历史人工发布须如实标为人工路径，并关联真实证据；不得为“对齐”而补造队列执行成功历史。验收目标是“无未解释差异”，不是抹平所有历史差异。

自动同步保留人工负责人、运营状态、备注和待办。重复运行不新增重复发布，不删除人工内容。生产表写入在授权范围内执行并回读核验。

## 六、四个运营循环

### 6.1 生产循环

把已有构建、验证、暂存、发布 PR、部署核验和归档能力连接成受支持的入口。第一步调查现有 Web Publish 的真实覆盖，复用已交付的版本生命周期、健康与回执能力，只补集成缺口；不重新包装已有命令来冒充自动化。

完成标准：可重复执行、失败可定位、可继续或安全重试、产物可追溯。一个命令仅是入口体验，不是完整验收标准。

### 6.2 修订循环

云文档改动首先通过现有回写机制进入审核派生文件和审核分支。可复用模板修正、业务源数据更新分别走对应流程和审批，不把所有审核改动直接写回公共模板。

保留删除检查、差异复核、写后回读及基准更新。完成标准是修订在后续构建中正确保留，同时没有污染不适用的其他目标。

### 6.3 翻译循环

每轮修订收集候选译文 → 标注源句、语言、适用范围及来源 → 审核 → 入 TM-B → 下次预翻译复用 → 验证效果。

建议每月固定审核一批，与交付周期配合。先验证积压清单，不承诺所有条目都应入库；可拒绝、合并或保留为特定型号用语。

分别衡量候选审核率、批准入库数、实际命中率和人工修正率。入库数量增长不等于翻译质量或节省工时已经改善。

### 6.4 运营反馈循环

近期按整本说明书及目标语言分析。章节阅读、搜索无结果、下载点击、语言切换和用户反馈须在相应采集能力落实后才可报告。

每月复核热点目标及异常，记录“需要改进／需要调查／无需动作”的判断；不要求热门前三名强行产生工单。

优先级综合：内容准确性与安全问题、业务交付要求、客服反馈、访问证据、复用收益和实施成本。低流量不会降低已确认错误的修复优先级。

统计约束：PV 不等于人数；Visits 不等于独立用户；根别名访问不保证来自扫码；别名跳转与正文可能重复计数；流量上升不能单独证明出货增长。无数据与零访问分开表达。

## 七、区域与语言扩展

按“已批准来源可用、真实交付需求、现有结构支持、上线可达性、验证成本”选择试点，不固定五个区域的全局排序。

| 对象 | 建议做法 | 进入条件 |
|---|---|---|
| 欧规剩余目标及语言 | 继续现行范围，先排除已经完成的目标 | 当前发布清单与源文件范围明确 |
| 中规、日规 | 可作为优先候选，按实际就绪度择一或小规模并行 | 指定型号有现行源内容，入口和访问方式明确 |
| 韩规 | 先核实现行目标与已完成修复，选择具体型号推进 | 真实阻塞已确认且有对应来源 |
| 巴西规、台湾规 | 按批准版本和业务需求接入 | 产品配置、术语及当地适用内容得到确认 |

台湾版本可以复用适用的中文内容，但不默认等于简体转繁体。巴西等区域的法规事项由具体产品适用范围决定，不把未确认法规要求写成所有产品的统一技术门槛。

大陆可达性应实测页面、资源、下载和统计链路；域名与托管由 IT 协同决定。印刷前优先确定组织可控制的稳定入口与迁移方案，不把托管商地址直接作为不可变依赖。

按型号×区域×语言列出内容、插图、装配和验收工作量，不把所有工作隐藏在“补译文”中。

## 八、短中长期路线图与 Checklist

### 0–30 天：统一发布入口并建立可信基线

- [ ] 对齐 HT-Manuals / HT-Doc 的文档身份、版本与旧新 URL，复核截图中的托管关系。
- [ ] 核查 HTML_link、印刷二维码及历史交付链接；区分最新版入口与历史版本链接。
- [ ] 验证兼容跳转或兼容页、正文、资源和语言入口，再按批准范围停止旧站独立更新；保留候选 publish 分支及恢复记录。
- [ ] 生成同一时点的产品、区域及语言覆盖清单；核实原方案数字和型号阻塞。
- [ ] 调查现有 Web Publish、月报调度、归档和目录同步能力，明确已完成与真实缺口。
- [ ] 执行 M0，建立已知历史差异清单；保留真实发布路径。
- [ ] 基线确认后，同期复用或补齐 M1/M2 的最小闭环：发布证据登记、幂等同步、失败重试及差异核对。
- [ ] 明确发布批准、部署成功和线上验证状态，打通实际版本核验。
- [ ] 选择一本已上线说明书，复核已有修订、发布和回退证据；仅对真实缺口或变化部分安排新演练，区分隔离环境与生产操作。
- [ ] 落实 M4/M5：稳定入口映射、统计口径及快照保存。
- [ ] 核实译文候选清单，完成首批审核，记录批准、拒绝和待定结果。
- [ ] 确认大陆访问试验与 IT 决策事项；选定下一批明确目标。

验收：两种接入方式的新发布均进入约定站点，旧链接有去向、历史版本可追溯、迁移可恢复；代表目标全流程有证据；重复执行不重登、不覆盖人工字段；失败可定位和重试；存量无未解释差异；统计缺失和口径差异明确可见。

### 30–60 天：降低批量维护成本

- [ ] 将已验证发布流程应用到不同结构的代表目标，检查通用性。
- [ ] 完善 M3，验证装配选择与冻结输入的一致性。
- [ ] 建立共享组件变化影响清单，明确需要重建、回归和重新审核的目标。
- [ ] 运营表增量更新目录和访问数据，保护人工维护字段并保存每期证据。
- [ ] 执行第一轮月度复核，形成有理由的行动或无需动作记录。
- [ ] 用审核后的 TM 条目完成一次实际复用，记录命中与修正情况。
- [ ] 完成新区域代表型号的 Web 交付；不在试点未稳定时全面铺开。
- [ ] 选择 IDML 代表产品族，形成组件、分页、字体及溢出验收清单。

验收：至少跨代表结构验证发布流程；新增目标人工操作可计量；组件修改影响范围可说明；译文有实际复用证据；试点输出符合对应格式要求。

### 60–90 天：按证据扩大覆盖

- [ ] 根据交付需求和试点成本，扩大区域、语言与型号覆盖。
- [ ] 比较人工干预、更新周期、返工与故障恢复指标，定位下一项瓶颈。
- [ ] 按真实内容问题执行插图和组件修复，不做无差别去文字化。
- [ ] 在有明确分析用途时补充搜索、下载、反馈等事件，记录隐私和保留边界。
- [ ] 对内容改进建立“问题—变更—发布—复核”记录，避免用小样本作因果结论。
- [ ] 完成 IDML 试点验收，决定扩展、继续打磨或暂缓。
- [ ] 完成一次恢复或环境冷启动演练，检查凭据、运行环境和维护交接。

验收：覆盖扩大时每目标人工负担没有同步增长；问题能追溯到发布及修订结果；关键操作有可复现路径；未完成的外部依赖有明确责任与状态。

### 3–6 个月：复用稳定与协作扩展

- [ ] 基于已验证产品族扩展 IDML 及多格式交付，分别保留验收证据。
- [ ] 完善多语言变更传播、版本关联和适用范围控制。
- [ ] 将稳定操作交给受支持入口和运行任务，减少操作者盯执行。
- [ ] 与实际参与者验证审核、异常处理和交接流程。

### 6–12 个月及以后：按需求提供内容服务

- [ ] 在有消费团队和质量责任人时，对接官网、客服、知识检索等服务。
- [ ] 提供带版本、适用范围和来源引用的内容接口或导出。
- [ ] 只有实际吞吐、维护或权限需求证明必要时，才考虑服务拆分和基础设施扩展。

长期阶段以组织需求和维护能力触发；不把新增平台功能当作必须完成的债务。

## 九、指标与人机分工

| 指标 | 统计方式与目的 |
|---|---|
| 每次发布人工干预次数 | 记录启动、排错、手动补登等动作，观察重复劳动是否下降 |
| 更新交付周期 | 从修订批准到线上验证，另列等待审核和实际处理时间 |
| 新目标接入成本 | 分开记录内容准备、工程处理与人工验收时间 |
| 发布可靠性 | 首次成功率、失败类型、恢复时间、未解释差异数量与存续时间 |
| 内容复用效果 | TM 实际命中与修正率、共享组件修复覆盖及回归成本 |
| 使用与反馈 | 按明确口径记录整本文档访问、反馈和已采集事件，不等同销售或客服收益 |

先建立首月基线，再确定下降幅度或服务目标，不预设缺乏依据的百分比。

机器负责：采集、构建、契约检查、对账、同步、证据归档和异常提示。

内容责任人负责：正确性、适用范围、译文批准和修订验收。发布操作者负责发布决策与异常处理。IT 负责正式域名、外链、托管和云端执行凭据等协作事项。沿用既有记录中夏冰作为发布健康和反馈责任人的安排；新增工作包的工程执行人、内容责任人、IT 对接人及备份人仍须登记，不推定其已接受任务。

每轮修订完成检查与候选译文收集；每周复核失败和未解释差异；每月进行一次内容与翻译复核；每季评估恢复能力、维护负担和下一阶段是否值得启动。正常运行尽量静默，避免用频繁通知增加负担。

## 十、实施边界与下一批任务

本次交付为方案文件及关联规划文档 PR。没有修改 Claude 原页面、Agent 操作规则、代码、线上表结构、托管设置、发布任务或定时任务；PR 合入也不等于站点迁移或生产写入获批。

建议下一批拆为三个可独立验收的工作包：

1. **WP1 发布现状、入口整合与对账基线**：核实两站目标、版本、现有能力和历史链接，形成迁移表；只读调查先行，托管与链接变更在具体范围获批后执行。
2. **WP2 发布登记与恢复闭环**：复用现有发布入口，补齐部署验证、目录幂等同步和重试；涉及工作流修改时按仓库规则确认具体变更。
3. **WP3 运营与译文首轮维护**：统一采集口径，验证自动更新方案，审核一批真实候选并完成复用验证。

执行顺序以工作包 1 的调查结果确定；已有能力直接复用，不重复立项。每个工作包应有明确范围、责任人、输入、输出、验收命令或证据、失败处理及回退方式。

### 10.1 工作包交付与启动门槛

| 工作包 | 启动依赖 | 交付物及验收证据 | 失败处理与回退 | 责任分工 |
|---|---|---|---|---|
| WP1 | 先采集同一时点基线，迁移子步骤待具体操作批准 | 两站配置/构建证据、目标及 URL/版本对应表、差异结论、变更前后访问记录；两条输入路径均核对发布 PR 与实际部署提交 | 未匹配目标保留旧入口；迁移失败恢复原映射/配置及批准快照；不删除候选分支 | 发布操作者验收；工程执行人和 IT 对接人开工前登记 |
| WP2 | WP1 确认真实缺口与字段/写入范围后启动 | 复用回执的设计差异、登记字段映射、重复运行不重登证据、同步失败只重试登记的证据、授权写入后的同记录回读 | 登记失败标记待重试，不重复发布；恢复机器字段同步前快照，保留历史发布和人工字段 | 工程执行人负责实现，业务数据责任人批准字段及写入范围 |
| WP3 | 核实数据访问和候选审核责任后可与 WP1 并行 | 统计窗口/过滤版本、目录快照、首批译文审核结论、实际 TM 命中及人工修正记录 | 采集失败标记 no_data，保留上一期；译文有疑义留待定，不批量覆盖批准记录 | 运营与语言内容责任人负责判断，执行人负责可追溯采集 |

工作包状态记录在执行路线中；本表定义交付契约，不维护另一份逐 PR 完成清单。
进入实施时按现有代码及文档确认验收命令，并把具体输入、输出、权限与回退写入切片 PR。
自动化未知时先输出设计和差异清单，不预先承诺新增工具或命令。

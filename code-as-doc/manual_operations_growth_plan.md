## 1. 定位：运维底座 ≠ 运营

#1103 交付的是运维底座——能发布、能修、能回滚、坏了知道（版本封存、健康巡检、反馈管线、部署回执）。它的主语是仓库和构建。

运营的主语是用户和业务。初版（2026-09-15 决策前）识别的三个缺口，后续决定与落地状态见 §5：

1. **没有任何访问数据**——看不见有没有人在用、在看什么。
2. **反馈渠道是 GitHub Issues**——消费者不会去 GitHub 提 issue，现渠道实际只服务内部。
3. **进入路径没有经营**——QR 码印了，但扫没扫、扫后走没走，一无所知。

一句话目标：**让对的人找到对的页 → 看得见他们的行为 → 把行为变成内容和产品改进 → 算得出省了多少客服成本。**

## 2. 用户与价值口

| 谁在看 | 什么时候看 | 运营价值 |
| --- | --- | --- |
| 新买家 | 开箱扫 QR | 首次体验、安全合规、注册 / 装 App 的引流口 |
| 遇到问题的用户 | 搜报错、查故障 | **客服工单分流（降本，最容易算钱的一项）** |
| 客服 / 售后同事 | 处理工单时引用 | 回答一致性、答复效率 |
| 搜索引擎来的人 | 购前研究、二手机主 | 品牌触点、SEO 资产 |

## 3. 能力分层（L1–L5）

### L1 数据层（第一优先，其余各层依赖它）

初版范围曾排除访客追踪；D1 已批准 Cloudflare Web Analytics 并记录配置激活，当前采集完整性与统计覆盖需另行核验，不重新请求该选择。

- 候选：Cloudflare Web Analytics（站点已在 Cloudflare 后面；免费、无 cookie、不采个人数据，合规负担最小，加一段 script 即可）；备选 RTD 商业版 traffic analytics。
- 当前先按整本/语言发布路径核对访问量与 Top 页面。站内搜索词、搜索无结果、下载点击及确定的 QR 来源须有相应采集证据后才能报告；语言分布不得从未验证的混语目录推断。

### L2 触达层（经营入口）

- QR 码：区分来源（包装扫码 vs 搜索进入）。静态站避免 query 采集，复用既有 alias 机制做来源别名路径。
- SEO：sitemap（RTD 自动生成，已有）；hreflang、页面 title、description、canonical、OG
  已于 2026-09-15 交付——全部从 L1 发布身份构建期派生，`site_base_url` 为域名切换的
  唯一开关。入口路径计数与链接归一已于 2026-09-16 交付：根别名=可计数的印刷/QR 入口层
  （noindex+canonical+beacon 发送窗口），Web Analytics 可按别名/嵌套路径分组，
  但根别名也会被分享，路径不能证明来自扫码，跳转与正文可能重复计数。对外链接三分规范
  （别名/嵌套/门户首页）写入 portal 文档；既有站内入口机制完成不等于跨 RTD 项目迁移已完成。
- 链接归一：官网 / App / 客服签名统一指向手册中心，不散链。

### L3 反馈层（渠道换成用户会用的）

- 页面"复制上下文"机制（#1110，五字段：型号 / 市场 / 语言 / 版本 / 页面）是可复用资产，只换渠道终点。
- 消费者渠道换成售后邮箱或官网客服表单（见 D2）；GitHub Issues 降级为内部 / 经销商渠道。
- 定响应 SLA（见 D4），先宽松起步再优化。

### L4 内容运营层（数据驱动迭代，依赖 L1）

- 每月先看整本/目标语言访问与真实反馈，记录需要改进、需要调查或无需动作。搜索无结果和章节峰值仅在相应事件已采集时分析；优先级同时考虑安全准确性、交付需求、客服反馈和维护成本，不按流量单独排序。
- 迭代走既有发布闭环，不新增流程。

### L5 业务联动层（远期）

- 公告 / 召回横幅能力（版本封存机制天然支持紧急插页）。
- 保修注册引流、客服知识库与手册同源化。

下表保留初版顺序；已交付能力不重新启动。本轮执行窗口及工作包状态以[执行路线](optimization_project.md)为准，已有 D1–D4 决定继续有效。

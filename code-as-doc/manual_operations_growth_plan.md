## 1. 定位：运维底座 ≠ 运营

#1103 交付的是运维底座——能发布、能修、能回滚、坏了知道（版本封存、健康巡检、反馈管线、部署回执）。它的主语是仓库和构建。

运营的主语是用户和业务。当前三个硬缺口：

1. **没有任何访问数据**——看不见有没有人在用、在看什么。
2. **反馈渠道是 GitHub Issues**——消费者不会去 GitHub 提 issue，现渠道实际只服务内部。
3. **进入路径没有经营**——QR 码印了，但扫没扫、扫后走没走，一无所知。

一句话目标：**让对的人找到对的页 → 看得见他们的行为 → 把行为变成内容和产品改进 → 算得出省了多少客服成本。**

## 2. 用户与价值口

| 谁在看 | 什么时候看 | 运营价值 |
| --- | --- | --- |
| 新买家 | 开箱扫 QR | 首次体验、安全合规、注册 / 装 App 的引流口 |
| 遇到问题的用户 | 搜报错、查故障 | **客服工单分流（降本，最容易算钱的一项）** |
| 客服 / 售后同事 | 处理工单时引用 | 回答一致性、答复效率 |
| 搜索引擎来的人 | 购前研究、二手机主 | 品牌触点、SEO 资产 |

## 3. 能力分层（L1–L5）

### L1 数据层（第一优先，其余各层依赖它）

现状：仓库刻意排除访客追踪（#1103 范围决策），需操作者拍板解锁（见 D1）。

- 候选：Cloudflare Web Analytics（站点已在 Cloudflare 后面；免费、无 cookie、不采个人数据，合规负担最小，加一段 script 即可）；备选 RTD 商业版 traffic analytics。
- 最小指标集：各型号访问量、Top 页面、站内搜索词、入口来源（QR / 搜索 / 官网）、语言分布。

### L2 触达层（经营入口）

- QR 码：区分来源（包装扫码 vs 搜索进入）。静态站避免 query 采集，复用既有 alias 机制做来源别名路径。
- SEO：sitemap、hreflang（多语言站直接影响搜索命中对的语言）、页面 title 规范化。均可构建期生成，不需要新服务。
- 链接归一：官网 / App / 客服签名统一指向手册中心，不散链。

### L3 反馈层（渠道换成用户会用的）

- 页面"复制上下文"机制（#1110，五字段：型号 / 市场 / 语言 / 版本 / 页面）是可复用资产，只换渠道终点。
- 消费者渠道换成售后邮箱或官网客服表单（见 D2）；GitHub Issues 降级为内部 / 经销商渠道。
- 定响应 SLA（见 D4），先宽松起步再优化。

### L4 内容运营层（数据驱动迭代，依赖 L1）

- 每月看：搜不到结果的 Top 搜索词（内容缺口）、高流量页的语言缺失（翻译优先级从拍脑袋变成按流量排）、故障排除页访问峰值（可能是产品批次问题的早期信号，反哺产品侧——说明书数据最值钱的用法）。
- 迭代走既有发布闭环，不新增流程。

### L5 业务联动层（远期）

- 公告 / 召回横幅能力（版本封存机制天然支持紧急插页）。
- 保修注册引流、客服知识库与手册同源化。

## 4. 节奏

| 阶段 | 内容 | 前置 |
| --- | --- | --- |
| 第 0 步 | 四项决策（见 §5），纯决策不动代码 | 无 |
| 第 1 月 | 接统计 + 定 KPI 基线（裸跑四周攒基线，什么都不改） | D1 |
| 第 2 月 | 入口经营（QR 来源区分、SEO 三件套）+ 反馈渠道切换 | D2 / D3 |

北极星指标（建议只设一个）：**手册自助解决率的代理指标**——故障排除页访问量 vs 同期客服工单量的比值变化。

## 5. 第 0 步决策清单（待操作者勾选）

每项决策落地前不实施任何对应改动；勾选后在"决策"行写结论与日期，实现切片引用本节。

- [x] **D1 访问统计**：是否开启站点访问统计？
  - 选项 A（推荐）：Cloudflare Web Analytics——免费、无 cookie、无个人数据，站点已在 Cloudflare 后面。
  - 选项 B：RTD 商业版 traffic analytics。
  - 选项 C：不开，维持现状（则 L1/L4 及北极星指标全部不成立）。
  - 决策：**选 A（Cloudflare Web Analytics）**　日期：2026-09-15。机制切片 #1151（默认关）；token 激活为后续 settings 变更，建议在 D3 绑定域名后建站取 token。
- [x] **D2 消费者反馈渠道终点**：访客复制上下文后贴到哪里？
  - 选项 A：售后邮箱（最低成本，客服团队现有流程可接）。
  - 选项 B：官网客服表单（体验最好，需官网侧配合）。
  - 选项 C：维持 GitHub Issues（等于放弃消费者反馈，仅内部使用）。
  - 决策：**选 A（售后邮箱 `hello@jackery.com`，出货手册已印的官方地址）**　日期：2026-09-15。切片 #1152；GitHub Issues 降级为内部/经销商分诊渠道。
- [x] **D3 自有域名**：是否将品牌域名绑定到 RTD 站点？
  - 选项 A：绑定（利于品牌信任与 SEO，需域名与 DNS 权限）。
  - 选项 B：暂用 RTD 默认域名（SEO 与品牌吃亏，零成本）。
  - 决策：**绑定**　日期：2026-09-15。执行 runbook 见 `code-as-doc/dev/rtd_custom_domain_runbook.md`（#1153）；最终域名与 DNS 权限两项输入待操作者补齐。
- [x] **D4 反馈响应 SLA**：对外承诺 / 内部执行的响应时限？
  - 建议起步值：3 个工作日内首次响应（先有再优化）。

# IDML Primary Font-Family Token Discovery (2026-07-31)

Scope: Workstream W / Stage 5 item 8.

## Finding

The same primary family was independently encoded in four production paths:

- `tools/idml/styles.py` selected the paragraph-style `AppliedFont`;
- `tools/idml/style_resources.py` declared the family and faces in
  `Resources/Fonts.xml`;
- `tools/idml/flow_idml.py` repeated the family for flow-only paragraph
  styles;
- `tools/idml/delivery.py` repeated the family, PostScript names, and licence
  in `fonts_manifest.md`.

That split allowed a future font-family change to produce an internally
inconsistent package even when each XML part remained structurally valid.

## Contract decision

`tools/idml/font_family.py` now owns one immutable primary-family token. The
production and flow styles, font resource declaration, and delivery manifest
all consume it. Symbol and circled-number fallback families remain separate
because they have different glyph and platform responsibilities.

This slice deliberately does **not** add a row to `data/layout_params.csv`.
Adding a token there would change the approved `layout_params_sha256` even
though the rendered family remains the same, which would turn this
zero-behaviour consolidation into a reference-layout approval event. A
language-specific CJK token remains a separate, operator-gated Stage 5 item.

## Safety evidence

The regression test locks the pre-change SHA-256 for:

- production `Styles.xml`;
- `Fonts.xml`;
- flow paragraph-style entries;
- the no-font-files delivery manifest.

It also scans the four former authority modules' Python string literals so the
primary family cannot silently become hardcoded there again. The default
family, face IDs, names, PostScript names, licensing text, and generated bytes
are unchanged.

# Hello-Docs 项目定位与能力边界

Updated: 2026-10-23

## 1. 本文角色与项目定位

本文供维护者与 Agent 理解 Hello-Docs 的起点、内容资源和实际能力边界。
项目定位以本文为准；具体实现状态与验收范围仍查对应契约、执行台账和验收记录。
本文不另建任务台账，也不替代长期战略、组件地图或操作指南。

**Hello-Docs 是一个以产品说明书为切入点，持续治理批准原稿、可复用模板与结构化内容，并支持资料生产、发布、查询和受控修订的内容管理系统。**

项目从拆解现有说明书、整理内容与组装结构开始，逐步积累模板、模块、骨架与多语言语料，
支持编写、翻译、评审和多格式交付。持续发布的内容又为后续编写、查询、比较与维护提供参考。
已有的生产和局部受控修订能力，与仍在建设的完整维护闭环，需要分别表述。

资料写作的主线在私有的资料开发工作台 Hello-Docs-Review：Agent 调用现有的基础设施、数据、
模板和语料起草，由人审核。基于数据和模板的自动构建退为按需使用的生产能力，
不是所有资料都必须先结构化的前提。

### 1.1 三个仓库与资料开发工作台

| 仓库 | 角色 | 职责 |
| --- | --- | --- |
| auto-manual（公开） | 工程面 | 代码、模板、共享组件、Skill、契约与 CI 只在这里修改；合入后单向同步到另外两个仓库 |
| Hello-Docs（公开） | 业务面 | 业务数据与语料资产、已发布的网页说明书、按需的多格式构建以及发布与追溯 |
| Hello-Docs-Review（私有） | 资料开发工作台 | 调用基础设施、数据、模板和语料，由 Agent 写作、由人审核；本仓库只维护 `docs/review-drafts/` |

工作台已有私有仓库与审核稿目录、私有审核站（2026-10-21 起），以及参考稿复用写作 Skill
（US→US 英文复用、US→JP 日文语料复用两种模式）。审核通过的工作台稿件作为批准原稿进入
Hello-Docs 发布与追溯，这一衔接是规划方向，尚未建设；在此之前，正式交付仍走 §5 的两条生产路径。
仓库、base 与同步通道的权威地图见[双平面地图](../../user-guide/two_plane_map.md)，
工作台的站点与编写规则见[审核稿私有站](../dev/rtd_manual_portal/review-drafts-site.md)。

## 2. 语料的范围与管理方式

广义语料是为编写、翻译与修订提供参考的内容资源集合，分布在模板、多维表和持续发布的
多语言 Web 文档中。这里的“语料库”不只指多维表中的翻译记忆表。

| 资源 | 提供什么 | 使用边界 |
| --- | --- | --- |
| 模板与组装结构 | 内容结构、通用表达、模块与骨架的复用方式 | 按现有模板、配置和适用目标维护；参考结构不证明目标产品事实相同 |
| 多维表中的内容与翻译语料 | 受管理的内容、参数、译文和术语 | 按各表已有的审核状态和适用规则受控复用 |
| 已发布的多语言 Web 文档 | 完整表达、章节上下文及具体市场、语言、版本的内容 | 同时承担交付与参考作用；引用保留出处，修正回到该版本声明的编辑入口 |

“翻译语料库”或“翻译记忆库”特指受管理的译文与术语资源；TM-B 是现行翻译记忆的规范写库，
不是上述全部广义语料的存储位置。来源和仓库分工见[双平面地图](../../user-guide/two_plane_map.md)，
译文管理见[翻译语料治理](../dev/translation_corpus_governance.md)。

广义语料可以用于写作参考；进入正式生产时，仍须确认目标适用性、权威来源和批准版本。
相似表达、检索结果或从网页抽取的数据，本身不构成新的批准依据。

## 3. 模板与内容资产的长期定位

说明书骨架、章节模板、共享组件、标准文案、术语和多语言语料，不只是构建输入，
也是可供资料开发人员和 Agent 理解、检索与复用的资料开发经验。
模板的价值包括结构规范、表达规范与适用规则：说明书如何组织、内容如何表达，
以及哪些内容能够在什么条件下复用。模板是工作台写作和批准原稿路径下编写与审核的直接参考，
也可用于按需的数据驱动自动构建；不要求所有目标迁入同一结构化生产方式。

模板复用必须核对目标产品能力、市场、语言、版本、权威来源与审核要求。
参考模板或相似产品文案不能自动证明目标适用，尤其是安全、警示、合规与规格事实。
对重要模板逐步补充用途、适用条件、可变内容、需要重新确认的事项和批准示例；
优先考虑风险、复用频率与维护成本，不要求一次性为每段文字建立登记。

上述规则是长期治理方向，不代表模板适用性推荐、自动审核或完整关系登记已经实现。
已有骨架继续维护；新骨架扩展仍遵守 [REV-41 暂缓决定](../dev/revitalization/rev41_skeleton_decision.md)。

## 4. 资料接入、治理与知识消费的方向

以真实业务价值而非自动生成数量决定投入优先级。已批准的原稿可保留原有编辑与设计路径，在声明权威来源、适用目标及版本后进入受控发布和追溯；结构化数据与模板驱动构建按需使用。不以跨产品批量参数替换作为普遍需求假设，也不要求所有说明书先完成全文结构化。

知识抽取面向明确的查询、关联、比较和复用需求，优先考虑产品、SKU、市场、语言、版本、规格与关键警示等高价值信息；保留原文与出处，抽取结果在核验前只是派生候选，不能取代 PLM 等企业权威事实或已批准原稿。普通叙述性内容可保持可检索引用，无需为了完整度拆成逐句记录。

系统价值应逐步从真实资料接入覆盖、发布与修订追溯、模板安全复用、知识查询效果、抽取核验质量和总维护成本衡量，而非仅按自动构建的说明书数量衡量。这些是后续规划和验收的方向，不代表跨区域知识抽取或完整治理闭环已经实现。

## 5. 已有的说明书生产能力

- **结构化拆解与装配：** 参数、表格、安全块、短文案等已有数据驱动机制，模板与配置承担
  页面及内容装配。长文仍部分由仓库模板维护，结构化与复用覆盖按内容类别和目标分别判断。
- **模块、骨架与共享组件：** 已有在用骨架单元及共享组件，Web 整本 Shared IR 与样式复用
  已形成。现有骨架继续维护，新一轮扩展按 [REV-41 决定](../dev/revitalization/rev41_skeleton_decision.md)
  暂缓；不能把 Web 发布覆盖直接当成骨架或结构化源覆盖。
- **工作台写作：** 资料开发工作台以参考说明书、目标规格书、模板和翻译语料起草审核稿，
  在私有审核站阅读；已实现 US→US 英文复用和 US→JP 日文语料复用两种模式。审核稿不是批准原稿，
  审核通过后转入发布的衔接尚未建设。
- **两条生产路径：** 受管理数据与共享模板可以冻结为快照后装配（按需使用）；批准的 PDF / AI 或 Git
  原稿也可以冻结为源包并构建网页版。每个目标声明自己的权威来源，无需先将全文迁入多维表。
- **多格式交付：** Web、Word、PDF、IDML 和 Markdown 已有各自路径，成熟度与验收范围不同。
  Web 是当前最成熟的持续交付链条，IDML 仍属印刷试生产；不能由一个输出端通过推定全部格式通过。

当前流程见[操作指南](../../user-guide/hello_auto-doc.md)，生产路径见
[Web 发布契约](../dev/web_publish_pipeline.md)，实际演进与输出边界见
[系统演进史](system_evolution_history.md)。

## 6. 已发布内容形成的派生视图

Hello-Docs 在生产与维护说明书的过程中，也整理产品和文档信息，方便检索、比较与维护。
这些能力承接已有内容积累，各视图继续按自己的来源规则更新。

- **产品矩阵：** 从已发布说明书读取规格，结合发布清单、能力配置及人工维护的分类与搭配
  关系形成视图。它不是所有字段都从正文自动推导的产品总表；引用规格保留原有市场、语言
  与版本范围，分类规则和来源见[产品矩阵](../dev/rtd_manual_portal/knowledge-pages.md#product-matrix-page)。
- **说明书数据：** 发布覆盖、语言版本、能力配置、素材登记和生产记录等按各指标来源汇总。
  登记量、配置引用、已发布数量与内容核对、实际采用及线上验收分别判断，口径见
  [数据统计](../dev/rtd_manual_portal/knowledge-pages.md#数据统计)与
  [网页说明书进度](../dev/rtd_manual_portal/web-progress.md)。
- **机读内容与观察：** 当前机读导出与查询仍限 EU，从已发布 HTML 提取语义内容；图片只消费
  已有 alt。它是派生消费面，不能表述为全部区域均可查询或全部内容直接由 IR 生成。
  具体范围与验收见[机读语料方案](../dev/machine_readable_manual_corpus.md)。

Web 是当前内容积累的重要载体；发布规模不代表全部产品、市场和语言齐套，也不代表
所有正文、图片信息或外部企业数据都已结构化接入。最新数量查发布清单和说明书工作台，不在本文维护第二份计数。

## 7. 内容维护闭环的实际边界

已有评审派生层、差异报告、受控回写、构建发布及追溯能力。云文档回写先进入允许修改的
评审派生层；共用模板同步与正式源表写入分别遵循自己的批准路径。批准措辞进入翻译记忆后，
也不代表所有冻结包自动更新：封存版本保持不变，修订须按声明的编辑入口重建并发布新版本。

EU 发现台账、回流跟踪、覆盖矩阵和核验工具已有实现；相关全量验收尚未完成。
更完整的内容关系登记、跨目标影响识别、变更传播和修正治理规则的反馈仍在建设中。
因此应分别说明“已有局部修订路径”“已实现工具”和“已完成具体闭环验收”。
现状与下一步查[知识治理方案](../dev/machine_readable_knowledge_governance.md)及
[执行台账](../dev/manual_revitalization_execution.md)，长期方向查
[系统演进战略](System%20Evolution%20Strategy.md)。

## 8. Agent 使用与维护规则

- 不得默认把扩大结构化覆盖、扩展骨架或增加自动构建路径视为优化目标；先核对真实业务需求、适用范围、维护责任与成本收益。
- 资料写作类任务（起草、改稿、参考稿复用）在 Hello-Docs-Review 工作台完成，遵守
  [`manual-review-draft`](../../.agents/skills/manual-review-draft/SKILL.md) 等 Skill；工具、模板或 Skill
  本身需要改时才到 auto-manual 提 PR。稿件不进入两个公开仓库。
- 首次接手仓库时阅读本文；涉及项目定位、能力总结、语料范围、架构、路线或对外介绍时重新核对。
- 涉及上述判断时引用本文相关章节，并从对应契约或台账核对具体实现及验收状态。
- “已实现”“局部实现”“建设中”“暂缓”分别表述；生产、批准、发布和线上验收证据分别判断。
- README 保持简短。产品矩阵、说明书数据及派生机制在本文和所属功能文档说明，不逐项展开为 README 宣传条目。
- 本文解释定位与边界；操作规则仍由根 [AGENTS.md](../../AGENTS.md)负责，组件归属查
  [组件地图](Hello_Docs_Architecture.md)，长期原则、执行状态和演进历史继续由各自文档维护。

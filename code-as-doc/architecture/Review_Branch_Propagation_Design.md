# Review-Branch Propagation Design

- Status: **approved**

- Implementation gate: **open for the bounded slices in §12**; propagation

This is the K15 design gate for Workstream V and Workstream W Stage 5 item 14.
It changes no current review branch, workflow, or build behavior. Implementation
PRs may be registered only after the approval record above is resolved.

## 1. Decision summary

Adopt a **pinned derivative** model:

- each review branch owns only one target's derivative under
  `docs/_review/<model>/<region>[/<lang>]`, including its approved overrides and
  propagation metadata;
- shared templates and manifests remain owned by `main` and are referenced by
  an exact, advanceable commit pin stored in the review manifest;
- a shared-source change creates one candidate bump PR per affected review
  branch, with that review branch as the PR base;
- the candidate is generated by a three-way, classify-or-abstain process and
  includes rendered before/after evidence;
- merging the bump PR advances that target's shared-source pin. No scheduler or
  bot writes directly to the review branch.

The review branch's Git ancestry is not the shared-source pin. Existing review
branches may remain far behind `main`; builds materialize the recorded shared
source separately and overlay only the target derivative.

## 2. Invariants

The implementation must preserve these boundaries:

1. **Derivative-only ownership.** A propagation PR may change only the resolved
   target directory under `docs/_review/**`. It may not commit `docs/_build`,
   shared templates, configs, source tables, or workflow files.
2. **Exact source identity.** A moving branch name such as `main` is never
   sufficient evidence. Every build and bump report names the exact source
   commit and frozen data-snapshot identity.
3. **Latest trusted toolchain, pinned content.** Automation executes code from
   the trusted current `main`, while shared content inputs are materialized from
   the recorded source commit. It never executes arbitrary code from a stale or
   reviewer-authored branch.
4. **Authored edits win or block.** A reviewer edit is preserved when the merge
   is provably disjoint. An overlap produces an abstention; it is never resolved
   by choosing the new template automatically.
5. **Evidence before cursor advance.** The shared-source pin advances only in a
   reviewable PR that carries machine reports and rendered comparison artifacts.
6. **No silent coverage holes.** Failure to enumerate branches, resolve a
   target, reproduce the old baseline, or classify a changed span is a visible
   blocked/abstained state, not a clean result.
7. **Reverse-sync boundaries remain intact.** Cloud-doc backport continues to
   route reviewer edits to review/source/template owners. Forward propagation
   never writes a phase2 source table or Translation Memory.

## 3. Review manifest contract

The existing target review manifest gains a versioned `propagation` object. The
field names below are the design contract; the implementation may add diagnostic
fields without weakening them.

```json
{
  "propagation": {
    "schema": "review-propagation/v1",
    "status": "active",
    "shared_source": {
      "repository": "Bingboom/auto-manual",
      "ref": "refs/heads/main",
      "commit": "<40-char commit sha>",
      "committed_at": "<RFC3339>"
    },
    "source_snapshot": {
      "sha256": "<phase2 snapshot sha256>",
      "archive_locator": "<immutable retrievable locator>"
    },
    "derivative": {
      "tree_sha256": "<canonical docs/_review target tree digest>",
      "baseline_sha256": "<unreviewed derivative digest at shared_source>"
    },
    "last_bump": {
      "from_commit": "<sha>",
      "to_commit": "<sha>",
      "pr_url": "<url>",
      "advanced_at": "<RFC3339>"
    },
    "migration": {
      "state": "native|legacy_pending|legacy_manual_first_bump",
      "note": "<optional reason>"
    }
  }
}
```

`shared_source.commit` is the cursor. `tree_sha256` detects branch changes after
planning. `baseline_sha256` identifies the authorless old derivative used for
the three-way comparison. `source_snapshot` is mandatory for unattended
regeneration; until E1 supplies a retrievable immutable snapshot, the target is
`legacy_pending` or a candidate abstains with `snapshot_unavailable`.

The old top-level `git_sha` remains readable during migration but is not an
advanceable propagation contract.

## 4. Content materialization

A propagation run uses three isolated trees:

| Tree | Inputs | Purpose |
| --- | --- | --- |
| `base` | old shared-source pin + pinned snapshot | authorless derivative before the shared change |
| `ours` | current target `docs/_review/**` at captured branch-head SHA | reviewer-authored derivative |
| `theirs` | candidate shared-source pin + the same pinned snapshot | authorless derivative after the shared change |

The current trusted `main` toolchain builds both `base` and `theirs`; an
allowlisted content materializer supplies shared templates, manifests, config
content, and other declared source inputs from the requested commit. No checkout
may silently fall back to current `main` content when the pin cannot be read.

The candidate pin is normally the `main` commit that contains the triggering
shared-source change. If later commits are included, the report lists the full
commit range and recomputes the affected-target set.

## 5. Affected-target discovery

The current path-token heuristic is useful as an alert but cannot own the new
contract. Candidate discovery must:

1. enumerate open review PRs from the configured authoritative repository;
2. resolve each branch to exactly one target using its review manifest and the
   live queue `Git_ref` binding;
3. derive the target's config, page manifest, recipes, snippets, and shared page
   dependencies using the same loaders as a build;
4. intersect the changed shared-source files with that dependency set; and
5. write one ledger row for every `(source change, review branch)` pair,
   including unaffected and unresolved outcomes.

Remote enumeration failure, duplicate target bindings, a missing manifest, or
an unknown dependency is not `unaffected`; it is `inventory_unresolved`.

## 6. Classify-or-abstain merge

Classification operates per file and then per changed span. A file is eligible
for automatic application only when every changed span has a safe class.

| Class | Evidence | Action |
| --- | --- | --- |
| `unchanged` | `ours == base` and `theirs == base` | no file change |
| `upstream_only` | `ours == base`, `theirs != base` | replace with `theirs` |
| `authored_only` | `ours != base`, `theirs == base` | preserve `ours` |
| `disjoint_merge` | authored and upstream edits touch distinct mapped spans | merge and verify both deltas survive |
| `parameter_refresh` | existing `merge_params` mapping is exact, only placeholder values changed, and the review line outside each placeholder equals `base` | substitute values and preserve surrounding authored content |
| `hard_preserve` | path is in `sync_preserve_paths` or under `overrides/**` | preserve and mark non-automatic |
| `conflict` | authored and upstream edits overlap | abstain |
| `unmapped` | rename/delete/page mapping or line mapping is ambiguous | abstain |
| `unreproducible` | base/snapshot/source input cannot be reconstructed | abstain |

Existing `merge_params` behavior is reused only after the stronger old-base
comparison proves the placeholder-bearing review line was not authored in the
same span. The existing behavior by itself is not proof because it can replace a
reviewer edit on that line.

Automatic deletion and rename are out of scope for the first implementation.
They always abstain. Binary and asset changes require exact old/new hashes plus
an unchanged review copy; any target override makes the file `hard_preserve`.

The aggregate candidate is `auto_applicable` only when all affected files are
safe. Otherwise the PR may still be opened as a report-only conflict PR, but it
must contain no speculative content resolution.

## 7. Candidate bump PR

For target branch `review/JE-1000F-US`, a candidate uses a short-lived head such
as `propagate/JE-1000F-US/<to-sha>` and sets the PR base to the review branch,
not to `main`.

The commit may contain only:

- changed files under the target's `docs/_review/**` directory;
- the updated propagation object in that target's manifest; and
- no locally generated reports or rendered artifacts.

The PR body and uploaded validation package contain:

- source repository, from/to commits, triggering file list, branch-head SHA,
  and snapshot identity;
- per-file and per-span classification with explicit abstention reasons;
- before/after page count, overset count, warnings, asset-lineage summary, and
  relevant content diff;
- rendered before/after PDFs plus page-image or visual-diff artifacts;
- the exact validation commands and reproducibility inputs; and
- the propagation-lag timestamps.

A zero-render-diff pin advance still uses a PR. It proves the branch was checked
and closes the ledger row without hiding the event.

Before push and again before merge, automation verifies that the target branch
head and `derivative.tree_sha256` still equal the captured values. If either
changed, the candidate becomes `stale` and is regenerated; it is never rebased
over new reviewer work blindly.

Propagation PRs are never self-merged. The operator or a future scoped owner
reviews content/compliance impact. CODEOWNERS distribution is a separate T6
dependency and cannot weaken that decision boundary.

## 8. Render and validation gates

Both old and candidate builds use the same frozen data snapshot, target, output
language, toolchain commit, and build flags. A candidate cannot be called clean
if either side fails to build.

Minimum machine gates:

1. manifest and source pins validate;
2. old derivative reproduces `baseline_sha256`;
3. merge classification has no unreported span;
4. authored deltas from `base -> ours` remain present after merge;
5. candidate build/check succeeds;
6. asset registry and source lineage pass;
7. page-count and overset signals are present when native InDesign evidence is
   required for that target; and
8. the rendered-diff package is complete and linked from the PR.

Native InDesign parity remains an operator/design-host gate for an approved
reference-layout target. A propagation worker may prepare IDML evidence but may
not invent or rebind layout approval.

## 9. Failure modes and required response

| Failure | Required state/action |
| --- | --- |
| authoritative repository unreachable | `inventory_unresolved`; alert, no clean report |
| review branch has no unique target binding | `target_ambiguous`; no candidate content |
| shared-source pin is missing or not an ancestor of candidate | `invalid_pin`; manual repair |
| frozen snapshot missing or hash mismatch | `snapshot_unavailable`; no regeneration |
| old derivative does not reproduce | `baseline_mismatch`; manual first bump |
| review branch changes during run | `stale`; discard candidate and rerun |
| authored/upstream overlap | `conflict`; report-only PR or human sync |
| page rename/delete or dependency mapping unknown | `unmapped`; abstain |
| rendered output loses content, adds overset, or changes unexpected pages | validation failure; block merge |
| bump PR closes without merge | ledger remains pending; pin does not advance |
| duplicate/legacy review branches | only queue-bound canonical branch proceeds; others remain visible |
| bot token can write outside target directory | hard failure and security incident; no push |

Retries must be idempotent on `(review branch, captured head, from commit,
to commit, snapshot sha256)`. A second run updates/reuses the same candidate PR
instead of creating an unbounded PR stream.

## 10. Propagation ledger and lag metric

The read-only ledger has one record per affected source-change/branch pair:

```text
source_commit, source_merged_at, changed_paths,
review_branch, review_pr_url, target, captured_head,
from_commit, to_commit, snapshot_sha256,
state, classifications, abstention_reasons,
bump_pr_url, discovered_at, opened_at, ready_at, advanced_at,
lag_seconds
```

State is one of `unaffected`, `pending`, `planning`, `ready`, `abstained`,
`blocked`, `stale`, or `advanced`. Unknown inventory is a blocked row, not an
omitted row.

For a branch, propagation lag is:

```text
advanced_at - source_merged_at
```

An unadvanced branch contributes to the outstanding age using `now -
source_merged_at`; it is not excluded from the metric. The dashboard reports:

- affected/advanced/outstanding branch counts and propagation completeness;
- median, p95, and maximum lag for advanced rows;
- age and target of the oldest outstanding row;
- blocked/abstained counts by reason; and
- branches whose pin is not at the latest applicable source commit.

The Workstream V pilot exit is three consecutive real shared-template changes
across one model family with every affected branch advanced, zero clobbered
authored edits, and visible lag records.

## 11. Migration of existing branches

Migration is target-by-target and does not interrupt unmigrated builds.

1. **Inventory and bind.** Enumerate open review PRs and live queue `Git_ref`
   values. Select one canonical branch per target; mark duplicates but do not
   delete them automatically.
2. **Enforce derivative ownership.** Open explicit cleanup PRs for non-review
   files. The current known case is four `_build` images on
   `review/JE-1000F-US`.
3. **Seed metadata without advancing content.** Validate the manifest's seed
   `git_sha` where possible and record `legacy_pending`. Do not claim it as a
   reproducible baseline without a retrievable matching snapshot.
4. **Manual first bump when needed.** If old inputs cannot reproduce the branch,
   an operator reviews one full old/current/candidate comparison and explicitly
   establishes the new pin, frozen snapshot, and baseline digest. Automation
   starts only after that evidence exists.
5. **Pilot one family.** JE-1000F is the natural candidate because it has active
   US/EU/JP/CN/pt-BR branches and the strongest existing build/IDML coverage.
   Final pilot choice remains an operator decision.
6. **Observe three real changes.** Keep every other family on the current path.
   Expand only after the Workstream V exit criterion passes.

## 12. Implementation slices after approval

Approval registers, but does not automatically execute, these bounded slices:

1. read-only propagation ledger JSON and current-state dashboard;
2. propagation manifest schema plus validator, with no writer;
3. pinned shared-content materializer and old-baseline reproduction proof;
4. three-way classify-or-abstain engine;
5. rendered comparison package generator;
6. report-only candidate PR creation for one pilot branch;
7. content-writing candidate PR behind the approval gate;
8. one-family migration and three-event pilot; and
9. dashboard lag roll-up and fleet expansion decision.

Each slice keeps unmigrated branches working. Workflow changes, bot write
permissions, E1 snapshot retention, and any auto-merge policy require their own
operator approvals.

## 13. Blast radius

The eventual implementation touches review branch semantics, build source
materialization, review manifests, PR generation, rendered comparison, and
dashboard reporting. It does not change the canonical phase2 source tables,
Translation Memory, shared-template ownership, reference-layout approval, or
publish approval.

The highest-risk boundaries are reproducible snapshot retrieval, preserving
reviewer edits, and correctly identifying every affected branch. All three are
fail-closed before any branch write.

## 14. Explicit non-goals

- No implementation in this design PR.
- No direct commits, force refreshes, or automatic rebases of review branches.
- No automatic conflict resolution, delete/rename propagation, or branch
  deduplication.
- No source-table, TM, or cloud-doc writes.
- No automatic approval, reference-layout rebind, or propagation PR merge.
- No fleet rollout before the one-family three-event pilot passes.
